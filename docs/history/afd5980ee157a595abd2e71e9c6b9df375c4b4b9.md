## 작업 배경

기존 보드는 하나의 Traffic Ingress가 요청 입구와 응답 도착점을 동시에 담당했다. 서버 처리와 DB 작업 뒤 응답이 생성되는 구조는 시뮬레이션에 있었지만, 보드에서는 요청이 다시 입구로 돌아가므로 요청과 응답의 방향 차이가 명확하지 않았다.

또한 처음부터 13×6 전체 격자를 사용할 수 있어 배치 공간이 별도 성장 자원으로 작동하지 않았고, LINK CAPACITY가 상점에 남아 있어 보유 인프라의 현재 용량을 한곳에서 확인하기 어려웠다. 작은 고정 글자와 보드 뒤 장식도 링크와 장비 상태의 시인성을 낮췄다.

## 요구사항

- 모든 사용자 표시 네트워크 연결 용어를 `링크`로 통일

- 최초 보드는 작게 시작하고 Credits로 확장

- 처리 성공을 플레이 중 즉시 확인할 수 있는 피드백 제공

## 주요 설계 결정

### 요청과 응답의 논리 경로 분리

보드 상단에 `Traffic Ingress`와 `Response Egress`를 고정 배치했다.

```text
Traffic Ingress
→ App Server
→ Primary DB
→ App Server
→ Response Egress
```

입구 연결은 파란 요청 링크, 출구 연결은 보라 응답 링크, DB 연결은 노란 데이터 링크로 표시한다. Load Balancer와 App Server 사이처럼 요청과 응답이 같은 물리 연결을 공유하는 구간은 링크를 두 번 그리지 않고 파랑·보라 이중선으로 표시한다.

### 성공 피드백

요청은 Response Egress에 도착해야 `completed`가 된다. 완료 시 출구에서 녹색 펄스와 `200 OK` 텍스트를 출력한다. 결과 화면에서는 기존 성공률, 평균 지연, Queue 수치와 함께 전체 요청 생명주기 완료 여부를 확인한다.

### 보드와 링크를 별도 성장 자원으로 분리

- BOARD LEVEL: 장비를 놓을 수 있는 격자 영역
- LINK LEVEL: 링크 하나의 최대 길이와 전체 링크 칸 예산

| BOARD LEVEL | 사용 영역 | 다음 레벨 비용 |
|---:|---:|---:|
| 1 | 7×4 | 90 |
| 2 | 10×5 | 140 |
| 3 | 13×6 | 없음 |

보드 밖 배치, 보드 밖 장비 연결, 연결된 장비의 보드 밖 이동은 Store와 시뮬레이션 검증 계층에서 거부한다.

### 하단 용량 제어

서비스 개시 Progress Bar 아래의 Inventory Dock을 세 영역으로 구성했다.

- 보유 장비와 배치 수
- LINK CAPACITY와 링크 색상 범례
- BOARD SIZE와 확장 버튼

상점은 웨이브 정보와 구매 상품에 집중한다.

## 알려진 제한사항

- 링크는 직교선으로 표현하지만 다른 장비나 링크를 피해 경로를 탐색하지 않는다.
- 보드 확장 셀은 즉시 나타나며 별도의 확장 애니메이션은 없다.
- 양방향 링크는 요청과 응답이 같은 용량을 공유하며 방향별 대역폭은 아직 계산하지 않는다.
- Burst 상황에서는 여러 요청의 `200 OK` 피드백이 겹칠 수 있다.
