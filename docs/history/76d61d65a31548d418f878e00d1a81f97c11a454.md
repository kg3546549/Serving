## 작업 배경

기존 프로토타입은 단일 서버 확장 상황과 소수 웨이브에 집중되어 있었다. 이를 여러 서비스 도메인을 순차적으로 학습하는 캠페인으로 확장하고, 요청이 서버에서 처리되는 순간 끝나는 구조를 실제 서비스 흐름에 가까운 `요청 → 서버 로직 → DB → 응답` 구조로 변경할 필요가 있었다.

## 주요 설계 결정

### 캠페인 난이도 순서

서비스 구현 시 필요한 상태 관리, 실시간성, 데이터 처리, 미디어 파이프라인 복잡도를 기준으로 다음 순서를 정의했다.

1. 기본 HTTPS API
2. WEB/WAS 분리
3. CDN과 콘텐츠 전송
4. MQTT IoT Telemetry
5. WebSocket 실시간 양방향 서비스
6. HLS/DASH VOD
7. RTMP/SRT 라이브 방송
8. RTSP 관제 플랫폼

Stage 2~8은 캠페인 메타데이터와 설계 범위로 정의하고, 이번 구현에서는 Stage 1을 완전한 플레이 범위로 선택했다.

### 요청 생명주기

요청 성공은 다음 순서를 모두 완료해야 성립한다.

```text
Traffic Ingress
→ App Server Queue
→ 비즈니스 로직 처리
→ Primary DB Queue
→ 읽기 또는 저장
→ Response 생성
→ 기존 경로 역방향 이동
→ Traffic Ingress 도착
```

서버 처리가 끝났더라도 DB 처리나 응답 반환 전에 Deadline을 넘기면 Timeout으로 처리한다.

### DB 역할

DB를 장식용 종착점이 아니라 별도 동시 처리 슬롯과 Queue를 가진 병목 시스템으로 구현했다.

- GET: 일반 읽기
- POST: 더 긴 쓰기 작업
- Slow Read: 인덱스가 없을 때 긴 처리 시간
- DB Index: 읽기와 Slow Read 단축, DB Queue 용량 확장

서버를 증설하면 DB 유입량이 증가하므로 후반 웨이브에서 병목이 서버에서 DB로 이동한다.
