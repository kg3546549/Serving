## 작업 배경

기존 보드는 배치된 모든 장비 사이에 링크을 자유롭게 만들 수 있었고, 연결 거리나 총 케이블 사용량에 제약이 없었다. 이 구조에서는 일반 App Server가 Load Balancer처럼 여러 트래픽 경로를 직접 분기할 수 있었고, 장비 위치와 네트워크 확장 비용이 게임 판단에 영향을 주지 않았다.

## 요구사항

- 일반 App Server가 여러 트래픽 링크을 직접 갖지 못하게 제한
- 여러 서버로 분기하는 역할은 Load Balancer에 집중
- 장비 종류별 링크 개수 제한
- 링크 하나의 최대 길이 제한
- 전체 링크이 사용하는 그리드 칸 수 제한
- 코인을 사용한 링크 용량 레벨업
- 기존보다 작은 셀과 더 많은 그리드 칸

## 주요 설계 결정

### 트래픽 포트와 데이터 포트 분리

App Server가 외부 트래픽 링크 하나와 DB 링크 하나를 동시에 가질 수 있도록 포트를 논리적으로 분리했다.

| 장비 | 트래픽 포트 | 데이터 포트 |
|---|---:|---:|
| Traffic Ingress | 1 | 0 |
| App Server A/B | 1 | 1 |
| Load Balancer | 3 | 0 |
| Primary DB | 0 | 2 |

App Server는 트래픽 포트 하나만 사용한다. App Server와 DB 사이의 연결은 별도 데이터 포트로 계산한다. Load Balancer는 Ingress 하나와 App Server 두 대를 연결할 수 있도록 트래픽 포트 세 개를 갖는다.

### 허용 토폴로지

다음 장비 조합만 직접 연결할 수 있다.

- Ingress ↔ App Server A
- Ingress ↔ Load Balancer
- Load Balancer ↔ App Server A/B
- App Server A/B ↔ Primary DB

Ingress와 DB, Load Balancer와 DB, App Server끼리의 직접 연결은 거부한다.

### LINK LEVEL

링크 길이는 두 노드의 가로·세로 차이를 더한 Manhattan 거리로 계산한다.

| Level | 링크 하나 최대 | 전체 링크 예산 | 다음 레벨 비용 |
|---:|---:|---:|---:|
| 1 | 4칸 | 8칸 | 60 |
| 2 | 6칸 | 22칸 | 100 |
| 3 | 9칸 | 36칸 | 없음 |

새 링크을 추가하거나 연결된 장비를 이동할 때 개별 길이, 전체 예산, 포트 수를 다시 검증한다. 조건을 위반하면 상태 변경을 거부한다.

### 그리드 밀도

보드를 9×4에서 13×6으로 확장하고 셀 크기를 줄였다. 초기 단일 서버 경로는 LINK LV.1의 전체 8칸을 사용하도록 기본 배치 간격을 설계했다. Load Balancer와 두 번째 서버를 포함한 분산 구조는 LINK LV.2 용량이 필요하다.

## 알려진 제한사항

- 포트는 실제 NIC나 운영체제 소켓 수가 아니라 게임용 논리 포트다.
- LINK 비용은 설치 비용만 적용하며 웨이브별 유지 비용은 아직 없다.
- 링크은 직교 형태로 표시하지만 장애물 회피 경로 탐색은 하지 않는다.
- 장비 종류가 늘어나면 포트 모델을 입력·출력 방향과 프로토콜별 슬롯으로 확장해야 한다.
