# 트래픽 웨이브·서버 캐릭터 상세 설계

> 문서 상태: 향후 확장 기획. 현재 프로토타입에 구현된 규칙은 [현재 구현 상세](./current-implementation-ko.md)를 우선한다.
>
> 목표: 서버가 실질적인 처리 타워가 되고, 보조 시스템을 적재적소에 배치해 대량 트래픽과 장애를 막아내는 게임 규칙 설계

---

## 1. 게임에서 실제로 흐르는 것은 무엇인가

화면에는 모두 귀여운 데이터 구체로 표현하지만 내부적으로는 역할을 구분한다.

```text
사용자 → HTTP 요청 → 로직 서버 → DB 쿼리 → 응답
                         └→ 메시지 큐 → Worker 작업
```

게임 전체에서 사용할 통합 명칭은 `트래픽 유닛`이다.

| 유닛 | 실제 의미 | 최종 처리 시설 |
|---|---|---|
| 일반 조회 | 페이지·API 조회 요청 | Logic Server |
| 데이터 쓰기 | 주문·회원가입·저장 요청 | Logic Server + Primary DB |
| 정적 콘텐츠 | 이미지·CSS·다운로드 | CDN 또는 Static Server |
| 로그인 | 인증 요청 | Auth Server |
| 대용량 작업 | 이미지 변환·정산·메일 | Queue + Worker |
| 실시간 연결 | WebSocket·게임 세션 | Realtime Server |
| 분석 작업 | 검색·집계·AI 연산 | Compute Server |

따라서 모든 유닛이 같은 서버에서 끝나지는 않는다.

서버는 타워디펜스의 공격 타워에 해당하지만 실제 표현은 다음과 같다.

```text
유닛을 끌어온다
→ 처리 슬롯에 넣는다
→ 일정 시간 작업한다
→ 완료 도장을 찍는다
→ 응답 유닛을 출구로 돌려보낸다
```

## 2. 트래픽 유닛 개별 애니메이션

## 2.1 모든 요청을 개별 유닛으로 표시한다

웨이브의 요청을 단순한 `600 RPM` 숫자로만 보여 주지 않는다.

각 요청은 입구에서 하나씩 생성되어 다음 상태를 직접 거친다.

```text
Spawn
→ Route 이동
→ 시설 검사
→ Queue 대기
→ Processing
→ Response 반환

또는

Drop / Timeout / Retry
```

요청 하나마다 다음 값을 유지한다.

- 고유 ID
- 요청 종류
- 현재 위치
- 목적 시스템
- 남은 제한 시간
- 처리 작업량
- 재시도 횟수
- 성공·실패 상태

## 2.2 화면 표현

| 유닛 | 외형 |
|---|---|
| 일반 조회 | 작은 파란 물방울 |
| 쓰기 요청 | 빨간 연필 모양 |
| 정적 파일 | 노란 사진 카드 |
| 로그인 | 보라색 자물쇠 |
| 긴 작업 | 큰 주황 상자 |
| 실시간 연결 | 꼬리가 긴 초록 유닛 |
| 봇 | 빠르게 떨리는 회색 유닛 |
| 공격 | 검은 가시 유닛 |
| 응답 | 하얀 날개 또는 체크 표시 |

유닛은 색상만으로 구분하지 않고 모양과 아이콘을 함께 사용한다.

## 2.3 이동 애니메이션

- 입구에서 작은 점으로 나타난 뒤 `뿅` 하고 커짐
- 경로의 곡선을 따라 통통 튀며 이동
- Load Balancer 앞에서 잠깐 멈춘 뒤 선택된 길로 회전
- 처리 시설에 들어갈 때 크기가 줄어들며 슬롯에 들어감
- 완료 후 응답 모양으로 바뀌어 반대 방향 또는 출구로 이동
- Timeout이 가까워지면 유닛 주변의 작은 시계 링이 줄어듦
- Retry가 발생하면 유닛 위에 작은 숫자가 붙고 입구 쪽으로 다시 이동

## 2.4 Queue 표현

요청이 서버 위에 겹쳐 보이지 않게 한다.

```text
처리 슬롯: 서버 몸체 안의 작은 창
대기 Queue: 서버 주변의 반원형 또는 지그재그 줄
```

Queue가 길어질수록:

- 줄이 서버 주변을 감쌈
- 요청 사이 간격이 좁아짐
- 서버 압력 링이 빨갛게 차오름
- 오래 기다린 유닛부터 시계 아이콘 표시

## 2.5 대량 웨이브에서도 개별성을 유지한다

수백 개 요청이 등장해도 하나의 큰 숫자로 합치지 않는다.

대신 화면 확대 수준에 따라 표현만 단순화한다.

| 화면 상태 | 표현 |
|---|---|
| 가까이 확대 | 얼굴, 요청 아이콘, Timeout 링 표시 |
| 기본 화면 | 색과 모양이 있는 작은 유닛 |
| 멀리 축소 | 개별 작은 점과 이동 방향만 표시 |

성능 구현에서는 Sprite Object Pool을 사용한다.

- 화면에 동시에 존재할 수 있는 유닛 상한 설정
- 완료된 Sprite 재사용
- 화면 밖 유닛은 저비용 업데이트
- 파티클은 성공·실패 순간에만 생성
- 시뮬레이션 상태와 렌더링 위치 분리

중요한 점은 렌더링이 단순해져도 유닛의 처리 상태는 각각 독립적으로 유지된다는 것이다.

## 3. 서버 처리량의 핵심 원리

서버 성능은 네 가지 값으로 설명할 수 있다.

### 처리 속도

한 요청을 완료하는 데 걸리는 시간이다.

```text
기본 처리 시간: 0.5초
```

### 동시 처리 슬롯

한 번에 몇 개의 요청을 처리할 수 있는지 나타낸다.

```text
동시 슬롯: 4개
```

### 대기열

처리 슬롯이 모두 찼을 때 앞에서 기다릴 수 있는 요청 수다.

```text
대기열: 12개
```

### 요청 작업량

모든 요청의 무게가 같지 않다.

| 요청 | 작업량 예시 |
|---|---:|
| 단순 상태 조회 | 0.25 |
| 일반 조회 | 1.0 |
| 데이터 쓰기 | 1.5 |
| 검색·집계 | 2.5 |
| 이미지 변환 | 5.0 |
| AI 추론 | 8.0 |

실제 처리 시간은 다음처럼 계산한다.

```text
실제 처리 시간
= 서버 기본 처리 시간 × 요청 작업량 ÷ 특화 보너스
```

### 이론 처리량

```text
초당 처리량
= 동시 처리 슬롯 ÷ 평균 처리 시간
```

예:

```text
동시 슬롯 4개
평균 처리 시간 0.5초

4 ÷ 0.5 = 초당 8건
8 × 60 = 분당 약 480건
```

게임 UI에는 `480 RPM`처럼 분당 처리량을 표시하고, 시뮬레이션 내부에서는 초 단위로 계산한다.

## 4. 요청이 쌓이는 이유

요청 도착 속도가 서버 처리 속도보다 높으면 대기열이 증가한다.

```text
분당 600건 도착
분당 480건 처리

매분 약 120건이 추가로 대기
```

지연 시간은 세 부분으로 구성한다.

```text
전체 지연
= 네트워크 이동 시간
+ 대기열에서 기다린 시간
+ 실제 처리 시간
```

플레이어는 서버 자체의 처리 속도만 높일 수 있는 것이 아니다.

- Firewall로 불필요한 요청 제거
- CDN으로 정적 요청을 입구에서 완료
- Cache로 반복 조회를 즉시 반환
- Load Balancer로 여러 서버에 분산
- Queue로 오래 걸리는 작업을 사용자 경로에서 분리
- Read Replica로 DB 읽기 분산
- Rate Limiter로 과도한 요청 제한

이것이 게임의 핵심 아키텍처 선택이다.

## 5. 과부하와 서버 OFF 시스템

### 5.1 서버 주변 원형 게이지

각 서버 주변에 항상 얇은 원형 상태 링을 표시한다.

| 상태 | 링 색상 | 의미 |
|---|---|---|
| 0~49% | 거의 투명한 민트 | 여유 있음 |
| 50~69% | 연한 노랑 | 처리 슬롯이 자주 참 |
| 70~84% | 주황 | 대기열 증가 |
| 85~99% | 연한 빨강→진한 빨강 | Timeout 위험 |
| 100% | 완전한 빨강 | 과부하 임계 상태 |

게이지는 단순 CPU만 나타내지 않는다.

```text
압력 게이지
= 처리 슬롯 점유율
+ 대기열 사용률
+ 메모리·연결 압력
+ 최근 Timeout 비율
```

권장 내부 계산:

```text
pressure =
  concurrencyRatio × 0.35
  + queueRatio × 0.45
  + resourceRatio × 0.20
```

대기열을 가장 크게 반영한다. 플레이어가 눈으로 요청이 쌓이는 현상과 링이 차오르는 현상을 연결할 수 있기 때문이다.

### 5.2 시각적 과부하 단계

### 안정

- 서버가 천천히 좌우로 흔들림
- 요청이 규칙적으로 들어오고 응답이 튀어나옴
- 얼굴이 편안함

### 바쁨

- 처리 슬롯이 모두 점등
- 작은 땀방울
- 처리음이 빨라짐
- 원형 링이 노란색으로 차오름

### 위험

- 앞에 요청 유닛이 눈에 보이게 줄을 섬
- 얼굴이 당황
- 주황색 증기
- 응답이 늦어지며 일부 요청 위에 시계 아이콘

### 임계

- 링이 진한 빨강으로 거의 완성
- 서버가 빠르게 떨림
- 경고음
- Timeout 요청이 회색으로 변해 사라짐
- 플레이어에게 3~5초의 대응 시간 제공

### OFF

- 링이 완성되며 `퐁!` 하는 연출
- 서버가 뒤로 살짝 튀고 연기 발생
- 얼굴이 `×_×`로 변경
- 서버 색상이 회색으로 변함
- 해당 서버로 들어가는 길이 닫힘
- 남아 있던 요청은 다른 경로로 이동하거나 실패

현실에서 서버가 물리적으로 폭발한다는 의미는 아니다.

게임의 OFF는 다음 현실 상황을 통합한 추상화다.

- 연결 슬롯 고갈
- 메모리 부족과 OOM
- 프로세스 크래시
- 응답 불능
- Health Check 실패
- 재시작 필요

도움말에서만 이 설명을 보여 준다.

### 5.3 OFF 이후

기본 서버:

```text
8초간 재부팅
→ 처리 중 요청 손실
→ 빈 상태로 복귀
```

업그레이드에 따라 달라진다.

- 빠른 재시작: 재부팅 시간 감소
- Graceful Shutdown: 처리 중 요청 일부 보존
- Health Check: Load Balancer가 OFF 서버를 즉시 제외
- Auto Recovery: 일정 시간 뒤 자동 교체
- Session Backup: 사용자 세션 유지

## 6. 서버 업그레이드 방식

### 6.1 수직 확장

기존 서버 한 대를 더 강하게 만든다.

| 업그레이드 | 효과 | 현실 개념 |
|---|---|---|
| 빠른 CPU | 처리 시간 감소 | Compute 성능 향상 |
| Core 추가 | 동시 슬롯 증가 | CPU Core·Worker 증가 |
| RAM 추가 | 대기열·세션 용량 증가 | Memory 확장 |
| 빠른 NIC | 큰 요청 이동 속도 증가 | Network Bandwidth |
| 냉각·안정화 | 압력 증가 속도 감소 | 자원 여유·안정성 |
| SSD | 파일·DB 작업 처리 개선 | Storage Optimized |

장점:

- 즉시 강해짐
- 구조가 단순함
- Load Balancer가 필요 없음

단점:

- 레벨이 높을수록 가격 급증
- 한 대가 OFF되면 전체 경로 중단
- 성장 한계가 있음

### 6.2 수평 확장

서버를 여러 대 배치한다.

```text
             ┌─ Server A
Request → LB ┼─ Server B
             └─ Server C
```

장점:

- 처리량 증가
- 한 서버가 OFF되어도 다른 서버가 처리
- 웨이브에 맞춰 서버 수 조절 가능

단점:

- Load Balancer 필요
- 서버 간 세션과 상태 문제가 발생
- DB 병목이 더 빨리 나타날 수 있음
- 유지 비용 증가

플레이어는 자연스럽게 수직 확장과 수평 확장의 차이를 경험하게 된다.

## 7. 서버 캐릭터 종류

서버는 단순히 등급만 다른 것이 아니라 처리 방식이 달라야 한다.

각 캐릭터는 실제 서버 또는 컴퓨팅 패턴에 대응한다.

---

### 7.1 올라운더 서버

**별칭:** 몽글이  
**역할:** 범용 Logic Server  
**현실 개념:** General Purpose Server

### 게임 능력

- 속도: 보통
- 동시 슬롯: 보통
- 대기열: 보통
- 비용: 낮음
- 모든 일반 요청 처리 가능

### 처리 애니메이션

요청을 한 칸씩 안으로 넣고 도장을 찍어 응답으로 돌려보낸다.

### 적합한 상황

- Stage 1
- 트래픽 유형이 아직 단순할 때
- 예산이 적을 때

### 업그레이드

- CPU 강화
- 슬롯 추가
- Stateless 모드
- Health Check

### 약점

특정 작업에는 전문 서버보다 효율이 낮다.

---

### 7.2 스프린터 서버

**별칭:** 토끼  
**역할:** 빠른 단일 작업 처리  
**현실 개념:** Compute Optimized / 높은 단일 코어 성능

### 게임 능력

- 속도: 매우 빠름
- 동시 슬롯: 적음
- 대기열: 작음
- 비용: 중간

### 처리 애니메이션

한 요청을 재빨리 낚아채고 고속으로 왕복시킨다.

### 적합한 요청

- 짧지만 CPU가 필요한 계산
- 낮은 지연이 중요한 요청
- 실시간 점수 계산

### 약점

한꺼번에 많은 요청이 오면 작은 대기열이 빨리 찬다.

### 게임성

빠른 단일 타깃 공격 타워처럼 느껴진다.

---

### 7.3 멀티코어 서버

**별칭:** 문어  
**역할:** 여러 요청 동시 처리  
**현실 개념:** Multi-process / Thread Pool / 다중 Worker

### 게임 능력

- 속도: 보통
- 동시 슬롯: 매우 많음
- 대기열: 보통
- 비용: 높음

### 처리 애니메이션

여러 팔이 요청을 동시에 잡아 각 처리 칸에 넣는다.

### 적합한 요청

- 일반 API 요청이 많이 들어오는 상황
- 처리 시간이 비슷한 요청
- Load Balancer 뒤의 주력 서버

### 약점

개별 요청은 스프린터보다 느리다.

### 업그레이드

- Worker 수 추가
- Worker별 메모리 증가
- 작업 스케줄러

---

### 7.4 비동기 I/O 서버

**별칭:** 해파리  
**역할:** 가벼운 연결을 대량으로 유지  
**현실 개념:** Event Loop / Non-blocking I/O

### 게임 능력

- 가벼운 요청 동시 처리: 매우 높음
- 네트워크 대기 요청: 매우 강함
- CPU 작업: 매우 약함
- 비용: 중간

### 처리 애니메이션

수많은 촉수에 가벼운 요청을 매달아 두고 응답 준비가 끝난 순서대로 돌려보낸다.

### 적합한 요청

- 간단한 API
- 채팅
- 많은 네트워크 연결
- 외부 서비스 응답을 기다리는 요청

### 약점

무거운 계산 요청 하나가 들어오면 전체 촉수가 느려질 수 있다.

### 자연스러운 학습

플레이어는 “동시 연결이 많다”와 “계산을 빠르게 한다”가 다른 능력이라는 것을 경험한다.

---

### 7.5 메모리 서버

**별칭:** 햄스터  
**역할:** 많은 상태·세션을 보관  
**현실 개념:** Memory Optimized Server

### 게임 능력

- 세션 슬롯: 매우 많음
- 데이터 보관: 강함
- 일반 계산 속도: 낮음
- 비용: 높음

### 처리 애니메이션

요청의 작은 토큰을 볼주머니처럼 저장하고 다시 온 사용자를 빠르게 알아본다.

### 적합한 요청

- 세션이 있는 사용자
- 큰 메모리 데이터
- 실시간 방 상태

### 약점

직접 모든 비즈니스 요청을 처리하기에는 비효율적이다.

### 실제 연결

독립 Logic Server라기보다 Session Store 또는 Memory-heavy Service로 구현할 수 있다.

---

### 7.6 배치 처리 서버

**별칭:** 붕붕이  
**역할:** 여러 작업을 모아서 한 번에 처리  
**현실 개념:** Batch Worker

### 게임 능력

- 개별 즉시 처리: 느림
- 묶음 처리: 매우 강함
- Queue 필수
- 비용: 중간

### 처리 애니메이션

Queue에서 같은 종류의 작업을 5~10개 끌어모은다.

가득 차면 풍선처럼 부풀었다가 `뿅!` 하고 한 번에 모두 완료한다.

폭탄처럼 보이지만 작업을 파괴하는 것이 아니라 묶음 처리하는 연출이다.

### 적합한 작업

- 이메일 발송
- 로그 집계
- 정산
- 썸네일 생성

### 약점

사용자가 즉시 결과를 기다리는 요청에는 적합하지 않다.

---

### 7.7 계산 특화 서버

**별칭:** 대장장이  
**역할:** 무거운 CPU 계산  
**현실 개념:** Compute Optimized Server

### 게임 능력

- 무거운 작업 속도: 매우 빠름
- 가벼운 요청 효율: 낮음
- 에너지 사용: 높음
- 비용: 높음

### 처리 애니메이션

무거운 요청을 모루 위에서 여러 번 두드려 작은 응답으로 변환한다.

### 적합한 작업

- 검색 랭킹 계산
- 압축
- 암호 처리
- 복잡한 집계

### 약점

단순 요청을 이 서버에 보내면 비용 낭비가 크다.

---

### 7.8 가속기 서버

**별칭:** 드래곤  
**역할:** 이미지·영상·AI 작업  
**현실 개념:** GPU / Accelerator Optimized

### 게임 능력

- 특정 대형 작업: 압도적으로 빠름
- 일반 요청: 처리 불가 또는 매우 비효율
- 설치 비용: 매우 높음
- 준비 시간: 김

### 처리 애니메이션

여러 이미지 또는 AI 요청을 한 줄로 세운 뒤 넓은 불꽃으로 병렬 처리한다.

### 적합한 작업

- 영상 변환
- 이미지 처리
- AI 추론
- 대규모 행렬 계산

### 게임성

후반부의 고가 범위 공격 타워 역할을 한다.

---

### 7.9 실시간 연결 서버

**별칭:** 거미  
**역할:** 오래 유지되는 연결 관리  
**현실 개념:** WebSocket / Realtime Gateway

### 게임 능력

- 연결 슬롯: 매우 많음
- 연결 유지 시간: 김
- 요청 처리 속도: 낮음
- 연결이 끊기면 사용자 유닛 손실

### 처리 애니메이션

사용자와 서버 사이에 실을 연결해 계속 유지한다.

### 적합한 요청

- 채팅
- 실시간 게임
- 라이브 알림

### 약점

일반 HTTP 요청까지 보내면 연결 슬롯이 낭비된다.

---

### 7.10 전문 마이크로서비스 서버

**별칭:** 장인  
**역할:** 한 종류의 요청만 매우 효율적으로 처리  
**현실 개념:** Specialized Microservice

### 게임 능력

- 지정 요청: 매우 빠름
- 다른 요청: 처리 불가
- 비용: 낮거나 중간

### 예시

- 결제 서버
- 검색 서버
- 인증 서버
- 알림 서버
- 이미지 서버

### 처리 애니메이션

자신의 문양과 일치하는 요청만 자석처럼 끌어온다.

### 게임성

경로 기반 Load Balancer와 조합해야 강해진다.

---

### 7.11 함수 서버

**별칭:** 구름콩  
**역할:** 요청이 올 때마다 작은 처리 유닛 생성  
**현실 개념:** Serverless Function

### 게임 능력

- 설치 공간: 거의 필요 없음
- 갑작스러운 소량 요청: 강함
- 요청당 비용 발생
- 대량 폭주 시 동시 실행 한도
- 처음 생성될 때 Cold Start

### 처리 애니메이션

요청이 들어오면 작은 구름 서버가 `퐁` 하고 생성되어 하나의 요청을 처리하고 사라진다.

### 업그레이드

- Reserved Concurrency
- Provisioned Concurrency
- Cold Start 감소
- 실행 시간 감소

### 약점

지속적인 대량 트래픽에는 유지 서버보다 비쌀 수 있다.

---

### 7.12 저장소 특화 서버

**별칭:** 두더지  
**역할:** 큰 파일과 디스크 작업 처리  
**현실 개념:** Storage Optimized Server / Object Storage Gateway

### 게임 능력

- 대형 파일 처리: 강함
- 일반 API: 약함
- 저장 용량: 큼

### 처리 애니메이션

큰 파일 유닛을 땅속 저장고에 넣거나 꺼내 보낸다.

### 적합한 요청

- 업로드
- 백업
- 영상 파일
- 로그 보관

## 9. 서버가 전투하는 것처럼 보이는 처리 연출

## 기본 처리

```text
요청 접근
→ 서버가 몸을 살짝 앞으로 기울임
→ 요청을 처리 슬롯로 흡수
→ 진행 점이 한 바퀴 회전
→ 응답을 반대편으로 통통 튕겨냄
```

## 서버별 개성

- 토끼: 요청 하나를 빠르게 낚아챔
- 문어: 팔마다 요청 하나씩 잡음
- 해파리: 촉수에 많은 요청을 매달아 둠
- 붕붕이: 작업을 모았다가 한 번에 `뿅`
- 대장장이: 무거운 요청을 두드려 처리
- 드래곤: 같은 유형 작업을 범위 처리
- 거미: 사용자와 긴 연결 실 유지
- 구름콩: 작은 복제 서버를 순간 소환

## 중요한 원칙

서버가 악성 요청을 총으로 쏴서 제거하는 연출은 피한다.

서버는 요청을 완료하는 타워다.

악성 요청을 차단하는 전투 역할은 Firewall, WAF, Rate Limiter가 담당한다.

## 10. 시설 클릭과 배치 애니메이션

## 클릭: 띠용

```text
0ms   Scale X 1.00 / Y 1.00
70ms  Scale X 1.12 / Y 0.86
150ms Scale X 0.94 / Y 1.10
240ms Scale X 1.04 / Y 0.98
320ms Scale X 1.00 / Y 1.00
```

동시에:

- 눈을 한 번 깜빡임
- 작은 별 또는 원형 파티클 3개
- 선택 링이 부드럽게 나타남
- 짧은 `뽁` 효과음

## 배치

```text
반투명 홀로그램
→ 슬롯 위에서 위아래로 둥실
→ 설치 확정
→ 위에서 통통 떨어짐
→ 바닥이 살짝 눌림
→ 연결 포트가 한 번 점멸
```

## 업그레이드

- 몸체가 잠깐 부풀어 오름
- 별 파티클
- 새로운 슬롯이나 장식이 실제 외형에 추가
- 능력치 숫자 대신 처리 슬롯 증가를 눈으로 보여 줌

예:

- Core 추가: 처리 창이 2개에서 4개
- RAM 추가: 대기 벤치가 길어짐
- Health Check: 작은 청진기 드론 생성
- Auto Scaling: 뒤에 복제 실루엣 표시

## 11. CDN은 어디에 배치해야 하는가

## 현실적 위치

CDN은 원본 서버 옆이 아니라 사용자와 가까운 네트워크 가장자리, 즉 게임 보드 입구에 둔다.

```text
                    ┌─ CDN Cache → 즉시 응답
사용자 요청 → Edge ┤
                    └─ Cache Miss → WAF/LB → Logic Server → DB
```

## 게임 보드 표현

CDN은 일반 경로 위의 타워보다 **입구 옆에 붙는 엣지 슬롯**으로 만든다.

캐시 가능한 요청이 들어오면:

1. CDN이 요청 문양을 확인한다.
2. 저장된 콘텐츠가 있으면 요청을 끌어온다.
3. 원본 서버까지 보내지 않고 입구에서 응답을 돌려보낸다.
4. Logic Server와 DB의 부하는 전혀 증가하지 않는다.

Cache Miss라면:

1. 요청이 원본 경로로 계속 이동한다.
2. 응답이 돌아올 때 CDN이 복사본을 저장한다.
3. 다음 같은 요청부터 CDN이 직접 처리한다.

## CDN으로 처리할 요청

- 이미지
- CSS와 JavaScript
- 다운로드 파일
- 공개 정적 페이지
- 캐시가 허용된 API 응답

## CDN으로 처리하면 안 되는 요청

- 회원가입
- 주문
- 결제
- 개인화된 최신 정보
- DB 쓰기
- 강한 일관성이 필요한 데이터

## 게임성

### 장점

- 수많은 정적 요청이 입구에서 사라져 화면이 시원하게 정리됨
- 원본 서버 부하 감소가 눈에 즉시 보임
- 먼 지역 요청의 이동 거리 감소

### 트레이드오프

- 설치와 유지 비용이 큼
- 첫 요청은 Cache Miss
- TTL이 길면 오래된 응답 제공
- Cache Key 설정이 나쁘면 Hit Ratio 감소

## CDN 업그레이드

| 레벨 | 기능 |
|---:|---|
| 1 | 이미지 캐시 |
| 2 | 저장 슬롯 증가 |
| 3A | TTL 증가 |
| 3B | 빠른 갱신 |
| 4 | 지역 Edge 추가 |
| 5 | Origin Shield |
| 6 | 원본 장애 시 오래된 캐시 제공 |

## 12. 다른 시스템의 적절한 배치 위치

```text
사용자
  ↓
[DDoS 방어]
  ↓
[CDN / Edge Cache]
  ↓
[WAF / Rate Limiter]
  ↓
[L4 또는 L7 Load Balancer]
  ↓
┌───────────────────────────────┐
│ Logic / Auth / Realtime 서버 │
└───────────────────────────────┘
       ↓                ↓
   [App Cache]       [Message Queue]
       ↓                ↓
 [Connection Pool]   [Worker Server]
       ↓
 [Primary DB / Read Replica]
```

## Firewall

외부 입구 가장 앞쪽.

불필요한 포트와 명백한 비정상 연결을 먼저 제거한다.

## WAF

HTTP 내용을 볼 수 있는 Edge 또는 Load Balancer 앞.

CDN과 하나의 Edge 시설로 합쳐 업그레이드할 수도 있다.

## Load Balancer

반드시 여러 처리 서버보다 앞.

서버를 추가했는데 Load Balancer가 없으면 새 서버로 요청이 자동 분산되지 않는다.

## App Cache

Logic Server와 DB 사이의 옆 경로.

Logic Server가 먼저 Cache를 확인하고 Miss일 때만 DB로 간다.

## Message Queue

Logic Server 이후 비동기 작업 경로.

사용자에게 즉시 `접수됨` 응답을 보내고 긴 작업은 Worker가 나중에 처리한다.

## Connection Pool

Logic Server 그룹과 DB 사이.

DB 연결을 재사용하며 너무 많은 서버가 DB에 동시에 접속하는 것을 제어한다.

## Read Replica

Primary DB 옆.

조회 요청만 분산하고 쓰기 요청은 Primary로 유지한다.

## Metrics Monitor

경로 위에 놓지 않는 지원 시설.

범위 안의 서버와 시스템 위에 처리량, Queue, 오류 정보를 표시한다.

## 13. 시스템별 시각적 처리 방식

| 시스템 | 화면에서 하는 행동 |
|---|---|
| Firewall | 악성 유닛을 작은 방패로 튕김 |
| Rate Limiter | 너무 빠른 묶음을 입구에서 잠시 세우거나 돌려보냄 |
| WAF | 요청 문양을 확대 검사하고 위험 패턴 제거 |
| CDN | 반복 정적 요청에 즉시 복사 응답 반환 |
| Load Balancer | 회전하며 요청을 여러 길로 던짐 |
| Logic Server | 요청을 처리 슬롯에 넣고 응답 생성 |
| Cache | 서랍에서 저장된 응답을 즉시 꺼냄 |
| Queue | 긴 작업을 줄 세워 보관 |
| Worker | Queue에서 작업을 가져와 처리 |
| Connection Pool | 재사용 연결 토큰을 서버에 대여 |
| DB | 쿼리를 읽거나 데이터를 기록 |
| Read Replica | 파란 조회 요청만 끌어감 |
| Circuit Breaker | 고장 서버 경로의 차단기를 내림 |
| Auto Scaling | 부하가 높으면 서버 복제본이 성장해 나타남 |

---

## 14. 웨이브 설계

## 웨이브는 처리량만 늘리면 안 된다

단순히 유닛 수만 늘리면 결국 서버 숫자만 늘리는 게임이 된다.

각 웨이브는 새로운 병목을 만들어야 한다.

| 웨이브 변화 | 요구되는 대응 |
|---|---|
| 일반 요청 증가 | 서버 업그레이드 |
| 순간 Burst | Queue 또는 여유 용량 |
| 정적 요청 반복 | CDN |
| 동일 조회 반복 | Cache |
| 쓰기 요청 증가 | Primary DB 강화 |
| 읽기 요청 증가 | Read Replica |
| 대형 작업 등장 | Worker·Compute Server |
| 장기 연결 등장 | Realtime Server |
| 봇 요청 등장 | Rate Limiter |
| 악성 요청 등장 | WAF |
| 서버 한 대 고장 | Load Balancer + Health Check |
| 재시도 폭풍 | Circuit Breaker |

## 15. 추천 캠페인 10개

## Stage 1. 작은 가게

### 제공 시설

- 몽글이 Logic Server 1대
- Primary DB 1대

### 트래픽

- 일반 조회 요청
- 최대 120 RPM

### 목표

요청이 서버에 들어가 처리되고 DB를 다녀와 응답으로 돌아가는 기본 흐름을 본다.

서버 하나로 충분히 클리어된다.

### 자연스럽게 배우는 것

- 서버가 요청을 처리한다.
- DB 조회가 추가 시간을 사용한다.
- 서버에는 동시에 처리할 수 있는 수가 있다.

---

## Stage 2. 점심시간

### 변화

- 트래픽 300 RPM
- 짧은 Burst 발생

### 새 기능

- CPU 업그레이드
- Core 업그레이드
- Queue Buffer 업그레이드

### 선택

- 빠른 CPU로 개별 처리 단축
- Core를 늘려 동시 처리 증가
- Buffer를 늘려 순간 Burst 흡수

### 자연스럽게 배우는 것

처리 속도, 동시성, 대기열은 서로 다른 능력이다.

---

## Stage 3. 첫 번째 확장

### 변화

- 트래픽 600 RPM
- 서버 한 대의 최대 성장 한계

### 새 시설

- Load Balancer
- Logic Server 추가

### 퍼즐

서버만 추가하면 아무 요청도 가지 않는다.

Load Balancer를 앞에 설치하고 두 경로를 연결해야 한다.

### 자연스럽게 배우는 것

- 수평 확장
- 부하 분산
- 단일 장애 지점

---

## Stage 4. 인기 상품

### 변화

- 같은 상품 조회 요청이 반복
- DB 읽기 부하 급증

### 새 시설

- App Cache

### 퍼즐

서버를 계속 늘려도 DB 앞에서 요청이 쌓인다.

Cache를 Logic Server와 DB 사이에 연결하면 반복 조회가 DB까지 가지 않는다.

### 자연스럽게 배우는 것

- Cache Hit / Miss
- TTL
- 서버 병목을 해결하면 DB가 다음 병목이 될 수 있음

---

## Stage 5. 이미지 축제

### 변화

- 이미지와 정적 파일 요청이 전체 트래픽의 70%
- 먼 지역 사용자 등장

### 새 시설

- CDN
- Static Server

### 퍼즐

CDN을 서버 뒤에 놓으면 효과가 거의 없다.

입구 Edge 슬롯에 설치해야 정적 요청이 원본에 도달하기 전에 처리된다.

### 자연스럽게 배우는 것

- Edge
- Origin
- Cache Hit Ratio
- CDN은 모든 동적 요청을 대신하지 않음

---

## Stage 6. 주문 폭주

### 변화

- DB 쓰기 요청 증가
- DB 연결 수 고갈

### 새 시설

- Connection Pool
- DB Index
- Read Replica

### 퍼즐

- 읽기는 Replica로
- 쓰기는 Primary로
- Pool이 너무 크면 DB가 과부하

### 자연스럽게 배우는 것

- 읽기와 쓰기 분리
- DB Connection
- 인덱스의 읽기 이점과 쓰기 비용

---

## Stage 7. 느린 작업

### 변화

- 이메일, 영수증, 이미지 변환 작업 등장
- Logic Server 슬롯이 긴 작업에 묶임

### 새 시설

- Message Queue
- 붕붕이 Batch Server
- 대장장이 Compute Server

### 퍼즐

느린 작업을 사용자 요청 경로에서 분리한다.

### 자연스럽게 배우는 것

- 동기와 비동기
- Queue Buffer
- Worker 수와 Queue 길이

---

## Stage 8. 로그인 공격

### 변화

- 봇 로그인 요청
- 공격 패턴 요청

### 새 시설

- Rate Limiter
- WAF
- Auth Server

### 퍼즐

모든 요청을 서버에서 검사하면 Logic Server가 먼저 과부하된다.

입구에서 불필요한 요청을 걸러야 한다.

### 자연스럽게 배우는 것

- 조기 차단
- Rate Limit
- 정상 사용자 오탐

---

## Stage 9. 연쇄 장애

### 변화

- Logic Server 하나가 간헐적으로 느려짐
- 실패 요청이 Retry를 생성

### 새 기능

- Health Check
- Outlier Detection
- Circuit Breaker
- Auto Scaling

### 퍼즐

무제한 Retry는 요청 유닛을 더 많이 만들어 전체 시스템을 무너뜨린다.

### 자연스럽게 배우는 것

- 장애 격리
- Retry Storm
- Warm-up과 Scaling Delay

### 변화

- 정적·동적·쓰기·실시간·배치 요청 혼합
- 지역 장애 이벤트

## 16. 학습을 가르치지 않고 녹이는 방법

## 설명 전에 현상을 보여 준다

좋지 않은 방식:

> 로드밸런서는 트래픽을 여러 서버로 분산합니다.

게임 방식:

1. 서버를 한 대 추가한다.
2. 새 서버로 요청이 가지 않는다.
3. 플레이어가 빈 경로를 본다.
4. Load Balancer 아이콘이 살짝 흔들린다.
5. 배치하면 트래픽이 두 길로 갈라진다.

설명은 플레이어가 `?`를 눌렀을 때만 보여 준다.

## 개념 이름보다 결과를 먼저 해금한다

처음에는:

```text
여러 길로 나누기
```

사용 후 도감에:

```text
Load Balancer
여러 서버에 요청을 나누는 실제 시스템
```

## 실패를 짧고 시각적으로 보여 준다

- 서버 앞에 줄이 생김
- 원형 링이 빨개짐
- Timeout 유닛이 회색으로 사라짐
- OFF 후 다른 서버에 트래픽이 몰림

긴 설명 팝업은 띄우지 않는다.

## 웨이브 종료 후 한 문장만 제공한다

예:

> 서버는 여유가 있었지만 DB 연결이 가득 찼어요.

옆의 `왜?` 버튼을 눌렀을 때만 상세 원리를 보여 준다.

## 도감은 플레이 후 열림

시설을 실제로 한 번 사용해야 현실 개념 카드가 해금된다.

카드 구성:

- 게임에서 한 일
- 현실에서 부르는 이름
- 잘 맞는 상황
- 주의할 점
- 실제 아키텍처 한 장

---

## 17. 실제 아키텍처를 보여 주는 방식

## 클리어 후 Blueprint

스테이지를 완료하면 플레이어가 만든 구조를 단순한 실제 아키텍처 그림으로 변환한다.

### 게임 화면

```text
귀여운 입구 → 빙글이 LB → 몽글이 A/B → 햄스터 Cache → DB
```

### Blueprint

```text
Client
→ Load Balancer
→ Application Servers
→ Redis Cache
→ Primary Database
```

설명은 한 줄만 기본 노출한다.

> 이 구조는 여러 애플리케이션 서버에 요청을 나누고 반복 조회를 캐시합니다.

## 실제 패턴 카드

### Scaled Web Application

```text
CDN/WAF
→ Load Balancer
→ Application Server × N
→ Cache
→ Primary DB + Read Replica
```

### Async Processing

```text
API Server
→ Message Queue
→ Worker × N
→ Object Storage / DB
```

### Resilient Service

```text
Load Balancer
→ Multi-Zone Server Group
→ Health Check
→ Auto Scaling
→ Replicated DB
```

이 카드는 시험 문제가 아니라 다음 스테이지의 새 시설 조합을 예고하는 보상으로 사용한다.

## 18. 도움말에만 표시할 교육 내용

## 서버 처리량

> 서버는 한 번에 처리할 수 있는 요청 수가 정해져 있어요. 들어오는 속도가 처리 속도보다 빠르면 앞에 줄이 생겨요.

## 동시 처리

> 처리 슬롯이 많으면 여러 요청을 같이 처리할 수 있어요. 하지만 요청 하나가 끝나는 속도와는 다른 능력이에요.

## Load Balancer

> 여러 서버 중 여유 있는 곳으로 요청을 보내요. 서버를 추가해도 연결하지 않으면 일을 받지 못해요.

## CDN

> 이미지처럼 반복되는 파일을 사용자 가까이 저장해요. 주문이나 저장 요청은 원본 서버로 보내야 해요.

## Queue

> 오래 걸리는 작업을 줄 세워 두고 Worker가 하나씩 처리해요. 사용자는 작업이 끝날 때까지 서버 앞에서 기다리지 않아도 돼요.

## Circuit Breaker

> 고장 난 서버에 계속 요청을 보내면 실패가 더 커져요. 잠시 길을 닫아 다른 시스템을 보호해요.

## 20. 첫 구현 권장 범위

처음에는 서버 캐릭터를 12종 모두 구현하지 않는다.

## 첫 프로토타입 4종

### 몽글이

범용 서버.

### 토끼

빠르지만 동시 슬롯이 적음.

### 문어

느리지만 동시 슬롯이 많음.

### 붕붕이

Queue의 작업을 묶음 처리.

## 첫 보조 시설 4종

- Load Balancer
- Cache
- Queue
- Metrics Monitor

## 첫 웨이브

```text
Wave 1: 몽글이 한 대로 처리
Wave 2: 순간 Burst로 Queue 발생
Wave 3: 서버 추가 + Load Balancer 필요
Wave 4: 반복 조회 → Cache 필요
Wave 5: 느린 작업 → Queue + 붕붕이 필요
```

이 다섯 웨이브만으로도 새 게임의 핵심 재미를 검증할 수 있다.

## 21. 최종 게임 감각

플레이어가 느껴야 하는 흐름은 다음과 같다.

```text
처음에는 요청이 통통 들어오고 서버가 즐겁게 처리한다.

요청이 많아지자 서버 앞에 줄이 생긴다.
서버 링이 노랗게 차오른다.

CPU를 올리니 빨라졌지만 다시 한계가 온다.
서버를 한 대 더 놓았지만 아무도 가지 않는다.

로드밸런서를 놓자 길이 둘로 갈라지고 요청이 분산된다.

이번에는 DB 앞이 막힌다.
캐시를 놓자 반복 요청들이 중간에서 바로 돌아간다.

느린 작업이 들어오자 Logic Server가 붙잡힌다.
Queue와 붕붕이를 놓자 작업이 옆길로 빠진다.

서버 하나가 OFF되지만 Health Check가 길을 닫고
나머지 서버가 계속 요청을 처리한다.
```

이 경험을 통해 플레이어는 별도의 강의 없이 다음 개념을 이해한다.

- 처리량
- 동시성
- 대기열
- 수직 확장
- 수평 확장
- 부하 분산
- 캐시
- 비동기 처리
- 장애 격리
- 비용과 안정성의 균형
