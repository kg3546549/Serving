## 1. 한 문장 정의

플레이어가 네트워크 토폴로지, 장비 상태, 패킷, 로그, 오류 메시지를 관찰하고 적절한 장비·프로토콜·설정을 선택하여 물리 연결부터 HTTP와 SSH까지 통신 경로를 단계적으로 완성하는 네트워크 퍼즐 게임이다.

핵심은 정답 버튼을 찍는 것이 아니라 다음 흐름을 반복하는 데 있다.

1. 현상을 관찰한다.
2. 어느 계층에 문제가 있는지 가설을 세운다.
3. 진단 도구를 사용해 증거를 수집한다.
4. 장비, 주소, 경로, 포트 또는 프로토콜을 설정한다.
5. 패킷 결과를 확인한다.
6. 최종적으로 서비스 또는 셸에 접근한다.

## 2. 반드시 바로잡아야 할 개념

### 2.1 OSI 7계층은 실제로 뚫는 일곱 개의 방화벽이 아니다

OSI 7계층은 통신 기능을 이해하기 위한 참조 모델이다. 현실의 인터넷은 TCP/IP 모델을 중심으로 구현되며, TLS나 ARP처럼 OSI 한 계층에 깔끔하게 들어맞지 않는 기술도 있다.

따라서 게임에서는 “각 계층을 공격한다”보다 **각 계층의 통신 조건을 해결한다**는 방식이 정확하다.

예를 들면 HTTPS 서버에 접근하려면 다음 조건이 차례로 만족되어야 한다.

- L1: 네트워크 인터페이스와 링크가 활성화되어 있다.
- L2: 같은 LAN 안에서 프레임을 전달할 수 있다.
- L3: 목적지 IP까지 경로가 있다.
- L4: 올바른 전송 프로토콜과 포트로 연결한다.
- L5~L6: 세션과 TLS 협상이 유효하다.
- L7: 올바른 HTTP 메서드, 호스트, 경로, 헤더를 보낸다.

이 조건을 게임 내부에서 `Layer Gate`로 구현한다. 하위 계층이 해결되지 않으면 상위 계층 도구가 단순히 “오답”을 표시하는 것이 아니라 실제와 유사한 실패 결과를 반환한다.

예:

- 링크 비활성화 → `LINK_DOWN`
- 경로 없음 → `No route to host`
- 닫힌 TCP 포트 → `Connection refused` 또는 TCP RST
- 필터링된 포트 → 시간 초과
- 잘못된 HTTPS 호스트명 → 인증서 이름 불일치
- 잘못된 HTTP 경로 → `404 Not Found`
- SSH 키 불일치 → `Permission denied (publickey)`

### 2.2 게임에서 사용할 계층별 표현

| 계층 | 학습 내용 | 대표 장비·도구 | 게임에서의 조건 |
|---|---|---|---|
| L1 물리 | 링크, 케이블, 전원, 신호 | 케이블 테스터, NIC, 광 모듈, AP | 장비가 물리적으로 연결되고 링크가 올라왔는가 |
| L2 데이터 링크 | Ethernet, MAC, 프레임, ARP, VLAN | 스위치, ARP 테이블, MAC 테이블 | 같은 링크에서 목적지 MAC으로 전달 가능한가 |
| L3 네트워크 | IPv4, 서브넷, 게이트웨이, ICMP, 라우팅 | 라우터, ping, traceroute, 라우팅 테이블 | 목적지 IP까지 경로가 존재하는가 |
| L4 전송 | TCP, UDP, 포트, TCP 상태 | 포트 프로브, TCP 핸드셰이크 뷰어 | 해당 전송 프로토콜과 포트로 연결 가능한가 |
| L5 세션 | 연결 상태, 인증 세션, 재접속 | 세션 관리자, SSH 연결 상태 | 대화 상태와 인증 컨텍스트가 유지되는가 |
| L6 표현 | 인코딩, 압축, 암호화, TLS 인증서 | 디코더, 인증서 검사기, TLS 분석기 | 데이터 표현과 암호화 협상이 유효한가 |
| L7 응용 | HTTP, DNS, SSH, API | HTTP 빌더, DNS 질의, SSH 클라이언트 | 응용 프로토콜 요청이 의미상 올바른가 |

주의 사항:

- ARP는 L2와 L3 경계의 기술로 설명한다.
- TLS는 교육상 L5~L6 관점에서 다루되, “OSI L6 전용 프로토콜”이라고 단정하지 않는다.
- SSH는 응용 계층 프로토콜이며, 내부적으로 전송·인증·연결 기능을 함께 제공한다.
- 초반 HTTP는 HTTP/1.1 또는 HTTP/2 over TCP만 사용한다. HTTP/3와 QUIC은 후속 스테이지에서 별도로 다룬다.

## 3. 게임의 세계관과 플레이 목적

플레이어는 가상의 사이버 훈련 기관에 소속된 네트워크 복구·보안 분석 요원이다. 모든 대상은 허가된 훈련망이며 실제 인터넷이나 다른 사용자의 장비와 연결되지 않는다.

각 임무는 단순 침입보다 다음 상황을 섞어 구성한다.

- 장애가 발생한 네트워크 복구
- 잘못된 설정 진단
- 허가된 침투 테스트
- 탈취된 서버의 원인 분석
- 제한된 단서를 이용한 내부 서비스 접근
- 패킷을 분석해 다음 경로 발견
- 올바른 인증 수단으로 원격 셸 접속

이렇게 하면 “해킹 느낌”은 유지하면서도 실제 네트워크 운영 지식과 보안 윤리를 함께 전달할 수 있다.

## 4. 핵심 플레이 루프

### 4.1 기본 흐름

```text
임무 확인
  → 토폴로지 관찰
  → 노드 또는 링크 선택
  → 진단 도구 실행
  → 로그·패킷·상태 변화 확인
  → 증거 노트에 단서 저장
  → 설정 또는 프로토콜 요청 구성
  → 새로운 네트워크 영역 해제
  → 최종 목표 달성
```

### 4.2 플레이어가 실제로 하는 행동

- 케이블, 인터페이스, 장비 모듈을 선택한다.
- IP 주소, 서브넷 마스크, 게이트웨이를 입력한다.
- ARP 테이블, MAC 테이블, 라우팅 테이블을 확인한다.
- ping이나 traceroute로 통신 경로를 조사한다.
- TCP 또는 UDP와 목적지 포트를 선택한다.
- TCP SYN, SYN-ACK, ACK 흐름을 관찰한다.
- DNS 질의를 보내 이름을 IP 주소로 변환한다.
- HTTP 메서드, 호스트, 경로, 헤더를 조합한다.
- TLS 인증서의 호스트명과 유효 기간을 확인한다.
- SSH 사용자, 포트, 키를 선택해 세션을 연다.
- 제한된 가상 셸 명령으로 임무 파일이나 로그를 조사한다.
- 캡처된 패킷의 Ethernet/IP/TCP/TLS/HTTP 헤더를 계층별로 펼쳐 본다.

### 4.3 승리 조건

스테이지마다 하나 이상의 명시적 조건을 둔다.

- 특정 서버와 정상 통신
- 올바른 HTTP 응답 수신
- 인증된 HTTPS 세션 수립
- SSH 셸 접속
- 지정된 로그 또는 플래그 파일 확인
- 잘못된 라우팅 또는 방화벽 규칙 수정
- 서비스 복구 후 검증 요청 성공

단순히 정답 문자열을 입력하는 방식은 피한다. 게임 엔진이 실제 네트워크 상태와 플레이어 행동의 결과를 검증해야 한다.

## 5. “때려 맞추기”를 막는 퍼즐 설계

### 5.1 모든 행동은 입력과 결과를 가져야 한다

도구 버튼을 누르는 즉시 성공시키지 않는다. 도구마다 다음 입력을 요구한다.

- 출발 인터페이스
- 대상 노드 또는 주소
- 프로토콜
- 포트
- 요청 옵션
- 사용할 인증 정보

결과는 성공/실패 한 줄이 아니라 다음 정보를 제공한다.

- 송신된 패킷
- 수신된 패킷
- 시간 초과 여부
- 장비 로그
- 변경된 세션 상태
- 새롭게 발견한 주소, 포트, 서비스, 사용자 또는 인증서

### 5.2 오답에도 원인이 드러나야 한다

좋지 않은 방식:

> 틀렸습니다. 다른 도구를 선택하세요.

좋은 방식:

> `10.0.20.15:22`로 TCP SYN을 보냈으나 응답이 없습니다.  
> 현재 패킷은 게이트웨이 `10.0.10.1`까지도 도달하지 못했습니다.

두 번째 방식은 플레이어가 포트보다 먼저 L3 경로를 조사해야 한다는 사실을 추론하게 한다.

### 5.3 도구 난사를 제한하는 자원

`Trace` 또는 `Noise` 수치를 사용한다.

- 진단 도구 실행 시 소량 증가
- 무작위 전체 포트 조사 시 크게 증가
- 정확한 대상에 제한된 프로브를 보내면 적게 증가
- 임계값을 넘으면 별점이 낮아지지만 스테이지가 즉시 실패하지는 않음

초보자가 학습을 중단하지 않도록 시간 제한과 즉시 게임 오버는 기본 캠페인에서 사용하지 않는다. 이후 도전 모드에서만 제한한다.

### 5.4 증거 기반 잠금 해제

강력한 도구는 버튼을 아무렇게나 누른다고 사용할 수 없게 한다.

예:

- TCP 도구를 쓰려면 먼저 대상 IP를 알아야 한다.
- SSH 도구를 쓰려면 열린 TCP 포트와 SSH 배너를 확인해야 한다.
- HTTPS 요청을 보내려면 TLS 세션이 수립되어야 한다.
- 인증 키를 사용하려면 임무에서 해당 키의 출처를 발견해야 한다.

이 방식은 “아이템 조합”이 아니라 네트워크 조사 과정 자체를 퍼즐로 만든다.

## 6. 실제 네트워크에서 단서가 되는 것

현실의 네트워크에도 명시적인 “힌트 버튼”은 없지만, 진단 결과와 프로토콜 응답이 단서 역할을 한다. 게임에서는 이를 의도적으로 읽기 좋게 표현한다.

| 관찰 가능한 단서 | 플레이어가 추론할 수 있는 내용 | 주의 |
|---|---|---|
| 링크 LED, 인터페이스 상태 | 물리 연결 또는 NIC 상태 | 링크가 올라와도 상위 계층 통신이 된다는 뜻은 아님 |
| ARP 요청·응답 | 같은 LAN에서 IP와 MAC의 관계 | ARP는 라우터를 넘어가지 않음 |
| MAC 주소 테이블 | 스위치가 어느 포트에서 장비를 학습했는지 | 실제 장비에서는 권한이 필요할 수 있음 |
| ping 응답 | IP 수준 왕복 경로가 동작할 가능성 | ping 차단만으로 호스트가 꺼졌다고 단정할 수 없음 |
| traceroute 결과 | 중간 라우터와 실패 지점 | 방화벽 정책에 따라 일부 홉이 보이지 않을 수 있음 |
| TCP SYN-ACK | 포트에서 TCP 연결을 받을 가능성 | 실제 서비스 종류는 추가 확인 필요 |
| TCP RST/연결 거부 | 호스트는 도달하지만 해당 포트가 닫혔을 가능성 | OS와 방화벽에 따라 반응이 다를 수 있음 |
| 시간 초과 | 경로, 방화벽, 서비스 중 하나의 문제 가능성 | 한 가지 원인으로 단정하면 안 됨 |
| 서비스 배너 | SSH, HTTP 서버 등 서비스 후보 | 배너는 숨기거나 위조할 수 있음 |
| DNS 응답과 TTL | 이름, 주소, 캐시 가능 시간 | DNS 정보만으로 서비스 정상 여부는 알 수 없음 |
| HTTP 상태 코드 | 요청 처리 결과와 다음 행동 | 본문과 헤더도 함께 봐야 함 |
| HTTP 응답 헤더 | 리다이렉트, 인증 방식, 콘텐츠 유형 | 헤더 이름과 의미를 학습 요소로 사용 |
| TLS 인증서 | 서버 이름, 발급자, 유효 기간 | 인증서가 유효해도 응용 서비스가 안전하다는 보장은 없음 |
| SSH 인증 오류 | 사용자 또는 인증 수단이 맞지 않음 | 무작위 비밀번호 대입을 정답으로 만들지 않음 |
| 서버·방화벽 로그 | 요청이 어디까지 도달했는지 | 후반부에서 방어자 관점 학습에 활용 |

핵심 힌트 문법은 항상 다음 형태로 유지한다.

> 관찰한 사실 → 가능한 원인 → 다음에 확인할 항목

정답을 즉시 말하기보다 조사 범위를 줄여 주는 것이 좋은 힌트다.

## 7. 힌트 시스템

### 7.1 4단계 힌트

#### 힌트 0: 환경 자체의 단서

별도 패널을 열지 않아도 보이는 단서다.

- 꺼진 링크 LED
- 빨간색 인터페이스
- 반복 전송되는 패킷
- 응답하지 않는 노드
- 잠금 표시된 서비스

점수 차감이 없다.

#### 힌트 1: 관찰 유도

어디를 봐야 하는지만 알려준다.

> 서버 포트보다 먼저 플레이어 단말의 인터페이스 상태를 확인해 보세요.

점수 차감이 거의 없다.

#### 힌트 2: 개념 힌트

필요한 네트워크 개념을 설명한다.

> 다른 서브넷의 목적지에는 직접 프레임을 보내지 않고 기본 게이트웨이로 전달합니다.

소폭 감점한다.

#### 힌트 3: 행동 힌트

다음 행동과 필요한 값의 일부를 알려준다.

> `10.0.10.1`을 기본 게이트웨이로 설정한 뒤 `10.0.20.15`에 ping을 보내세요.

별점 한 단계에 영향을 줄 수 있다.

#### 힌트 4: 해답 보기

전체 순서를 보여 주되, 직접 한 번 실행하도록 한다. 학습 기록에는 `Assisted Clear`로 표시한다.

### 7.2 자동 힌트 조건

- 같은 실패를 3회 반복
- 하위 계층 오류가 있는데 상위 계층 도구를 반복 사용
- 3분 이상 새로운 증거를 얻지 못함
- 확보한 단서를 열어 보지 않고 무작위 도구 사용

자동 힌트는 강제로 띄우지 않고 “분석 지원 사용 가능” 알림만 표시한다.

### 7.3 오개념 태그

스테이지와 실패 결과에 다음과 같은 태그를 붙인다.

- `link_vs_network`
- `mac_vs_ip`
- `same_subnet`
- `gateway_required`
- `icmp_not_service`
- `tcp_vs_udp`
- `port_vs_protocol`
- `dns_name_resolution`
- `http_method`
- `tls_identity`
- `ssh_authentication`

플레이어가 어떤 태그에서 반복 실패하는지 기록해 다음 스테이지의 보충 설명을 조정한다.

- 패킷 이동 애니메이션
- 현재 선택 계층만 강조

노드 종류:

- 플레이어 단말
- PC
- 서버
- 스위치
- 라우터
- 방화벽
- 무선 AP
- DNS 서버
- 웹 서버
- SSH 서버
- 외부망 또는 미확인 영역

### 8.3 Layer View

같은 토폴로지를 계층에 따라 다르게 보여 준다.

- L1: 케이블, 포트, 전원, 링크 상태
- L2: MAC 주소, VLAN, 프레임 흐름
- L3: IP 주소, 서브넷, 라우팅 경로
- L4: 활성 포트, TCP 상태, UDP 흐름
- L5~L7: TLS, 세션, 응용 서비스

이를 통해 플레이어는 “같은 네트워크를 서로 다른 추상화 수준으로 본다”는 개념을 자연스럽게 배운다.

### 8.4 도구함

도구는 계층별 탭으로 분류한다.

#### L1 장비

- 전원 검사
- 링크 테스트
- 인터페이스 활성화
- Ethernet 케이블
- 광 모듈
- 무선 어댑터

초반에는 케이블 색깔을 맞히는 문제가 아니라 장비의 포트 종류, 인터페이스 상태, 링크 유무를 판단하게 한다. 현대 Ethernet에서 항상 직결/크로스오버 케이블을 구분해야 한다는 식의 오래된 규칙은 핵심 정답으로 사용하지 않는다.

#### L2 도구

- ARP 요청
- ARP 캐시 확인
- MAC 테이블 확인
- VLAN 설정
- 프레임 상세 보기

#### L3 도구

- IP 설정
- 서브넷 계산기
- ping
- traceroute
- 라우팅 테이블
- 정적 경로 추가

#### L4 도구

- 제한 포트 프로브
- TCP 핸드셰이크
- UDP 데이터그램
- 연결 상태 보기
- 방화벽 규칙 검사

#### L5~L6 도구

- 세션 상태
- 재접속
- Base64/Hex 디코더
- 압축 해제
- TLS ClientHello 구성
- 인증서 검사

Base64는 암호화가 아니라 인코딩임을 명시한다.

#### L7 도구

- DNS 질의
- HTTP 요청 빌더
- HTTPS 요청
- SSH 클라이언트
- 제한된 가상 셸
- JSON/텍스트 응답 뷰어

### 8.5 패킷 인스펙터

하나의 패킷을 다음처럼 중첩 구조로 표시한다.

```text
Ethernet Frame
└─ IPv4 Packet
   └─ TCP Segment
      └─ TLS Record
         └─ HTTP Message
```

각 헤더를 펼치면 스테이지 수준에 맞는 필드만 먼저 보여 준다.

- 초급: 출발지, 목적지, 프로토콜, 포트
- 중급: TTL, TCP flags, sequence/acknowledgment
- 고급: window, checksum, TLS handshake, HTTP 헤더

### Stage 1. 불이 꺼진 링크

**주요 계층:** L1  
**목표 시간:** 5~8분  
**학습 목표:** 네트워크 통신 전에 링크와 인터페이스가 필요하다는 사실 이해

#### 상황

플레이어 단말과 스위치가 연결되어 있지만 단말의 Ethernet 인터페이스가 비활성화되어 있다. 서버 상태 페이지를 열어야 한다.

#### 제공 단서

- 단말의 링크 LED가 꺼져 있음
- 인터페이스 상태: `DOWN`
- HTTP 도구 실행 결과: `Network interface unavailable`
- 스위치 포트 상태: `No link`

#### 해결 과정

1. 단말 노드 선택
2. L1 보기로 전환
3. 올바른 Ethernet 인터페이스 활성화
4. 링크 상태가 `UP`으로 변하는 것을 확인
5. 미리 구성된 상태 확인 요청 실행

#### 승리 조건

- 단말과 스위치의 링크가 `UP`
- 상태 서버로부터 응답 수신

#### 단계별 힌트

- H1: 서버보다 먼저 단말과 스위치 사이의 선을 확인하세요.
- H2: IP 통신 전에 물리 인터페이스가 활성화되어야 합니다.
- H3: 단말의 `eth0`을 활성화하세요.

#### 방지할 오개념

- HTTP 버튼을 누르면 어떤 상태에서도 요청이 전송된다고 생각하는 것
- 서버 문제와 로컬 링크 문제를 구분하지 못하는 것

---

### Stage 2. IP는 아는데 MAC은 모른다

**주요 계층:** L2, ARP  
**목표 시간:** 8~12분  
**학습 목표:** 같은 LAN에서 IP 패킷을 Ethernet 프레임으로 보내기 위해 주소 해석이 필요함을 이해

#### 상황

플레이어와 파일 서버가 같은 서브넷에 있다. 서버 IP는 `192.168.10.20`이지만 ARP 캐시는 비어 있다.

#### 제공 단서

- 목적지 IP는 임무 문서에 표시
- ARP 캐시: 비어 있음
- 첫 프레임의 목적지 MAC을 결정하지 못한 상태
- 네트워크에 서버와 프린터가 함께 존재

#### 해결 과정

1. ARP 캐시 확인
2. `192.168.10.20`을 대상으로 ARP 요청 전송
3. ARP 응답에서 서버 MAC 확인
4. 서버로 전송되는 프레임에서 목적지 MAC 확인
5. 통신 검증

#### 승리 조건

- 올바른 IP-MAC 매핑 확보
- 서버가 응답한 프레임을 패킷 인스펙터에서 확인

#### 단계별 힌트

- H1: 같은 네트워크에서 실제 프레임은 IP 주소만으로 전달되지 않습니다.
- H2: ARP는 IPv4 주소에 대응하는 링크 계층 주소를 찾는 데 사용됩니다.
- H3: `192.168.10.20`으로 ARP 요청을 보내세요.

#### 방지할 오개념

- MAC 주소와 IP 주소를 같은 종류의 주소로 이해하는 것
- ARP 요청이 인터넷 전체로 전달된다고 생각하는 것

---

### Stage 3. 같은 주소처럼 보여도 다른 네트워크

**주요 계층:** L3  
**목표 시간:** 10~15분  
**학습 목표:** IP 주소, 서브넷 마스크, 기본 게이트웨이의 관계 이해

#### 상황

단말은 `10.0.10.50`이고 목적지 서버는 `10.0.20.15`다. 단말의 서브넷 마스크는 `/24`이지만 기본 게이트웨이가 비어 있다.

#### 제공 단서

- 같은 서브넷의 스위치 관리 주소에는 ping 성공
- 원격 서버에는 `No route to host`
- 라우팅 테이블에 `10.0.10.0/24` 경로만 존재
- 라우터 인터페이스 주소 `10.0.10.1` 표시

#### 해결 과정

1. 출발지와 목적지가 같은 `/24`가 아님을 계산
2. 라우팅 테이블 확인
3. `10.0.10.1`을 기본 게이트웨이로 지정
4. 목적지 서버에 ping

#### 승리 조건

- 기본 경로가 생성됨
- `10.0.20.15`에서 ICMP 응답 수신

#### 단계별 힌트

- H1: `10.0.10.50/24`와 `10.0.20.15/24`의 네트워크 주소를 비교하세요.
- H2: 다른 서브넷으로 가는 패킷은 라우터에 전달해야 합니다.
- H3: 기본 게이트웨이를 `10.0.10.1`로 지정하세요.

#### 방지할 오개념

- 앞부분이 비슷한 IP는 모두 같은 네트워크라고 생각하는 것
- 기본 게이트웨이를 목적지 서버 주소로 이해하는 것

---

### Stage 4. 패킷이 사라지는 지점

**주요 계층:** L3, ICMP, 라우팅  
**목표 시간:** 12~18분  
**학습 목표:** ping과 traceroute의 차이, 중간 경로와 라우팅 실패 지점 이해

#### 상황

세 개의 라우터를 거쳐야 하는 백업 서버가 응답하지 않는다. 두 번째 라우터에 목적지 네트워크 경로가 빠져 있다.

#### 제공 단서

- ping 시간 초과
- traceroute가 두 번째 라우터에서 중단
- 두 번째 라우터 로그: `No matching route`
- 목적지 네트워크: `172.16.30.0/24`
- 다음 홉 정보는 네트워크 다이어그램의 연결 주소에서 추론 가능

#### 해결 과정

1. ping으로 실패 확인
2. traceroute로 마지막 응답 홉 식별
3. 해당 라우터의 라우팅 테이블 확인
4. 목적지 네트워크로 가는 정적 경로 추가
5. ping과 traceroute 재실행

#### 승리 조건

- 목적지까지 경로 복구
- 변경 전후 traceroute 비교 완료

#### 단계별 힌트

- H1: 목적지만 보지 말고 패킷이 마지막으로 도달한 장비를 찾으세요.
- H2: traceroute는 TTL 만료 응답을 이용해 중간 경로를 관찰합니다.
- H3: 두 번째 라우터에 `172.16.30.0/24` 경로가 필요합니다.

#### 방지할 오개념

- ping 실패를 곧바로 서버 종료로 판단하는 것
- 모든 라우터가 모든 네트워크 경로를 자동으로 안다고 생각하는 것

---

### Stage 5. 문은 열렸지만 번호가 다르다

**주요 계층:** L4, TCP, 포트  
**목표 시간:** 12~18분  
**학습 목표:** IP 주소와 포트의 역할, TCP 연결 수립, 열린 포트와 닫힌 포트의 차이 이해

#### 상황

웹 관리 서비스가 표준 80번이 아닌 `8080/TCP`에서 실행 중이다. SSH는 `22/TCP`에서 실행 중이다.

#### 제공 단서

- 서버 IP까지 ping 성공
- `80/TCP`: 연결 거부
- `8080/TCP`: SYN-ACK
- `22/TCP`: SSH 형태의 서비스 배너
- 서비스 목록은 직접 공개하지 않고 제한된 후보 포트만 제공

#### 해결 과정

1. 네트워크 도달 가능성 확인
2. 후보 포트에 제한적으로 TCP SYN 전송
3. SYN, SYN-ACK, ACK 흐름 완성
4. `8080/TCP`를 웹 서비스로 기록
5. HTTP 도구의 목적지 포트를 8080으로 설정

#### 승리 조건

- 8080 포트에서 TCP 연결 수립
- 웹 관리 서비스의 첫 HTTP 응답 수신

#### 단계별 힌트

- H1: 서버에 도달하는 것과 원하는 프로그램에 연결하는 것은 다릅니다.
- H2: 포트는 한 호스트 안의 서비스 연결 지점을 구분합니다.
- H3: `8080/TCP`의 SYN 응답을 확인하세요.

#### 방지할 오개념

- ping 성공이 모든 서비스의 정상 동작을 의미한다고 생각하는 것
- 포트 번호를 물리적인 스위치 포트와 혼동하는 것

---

### Stage 6. 이름 뒤의 주소

**주요 계층:** L7 DNS, L4 UDP/TCP  
**목표 시간:** 12~18분  
**학습 목표:** 도메인 이름과 IP 주소의 관계, DNS 질의와 캐시 이해

#### 상황

임무 대상은 `archive.training.local`이지만 IP 주소는 알려지지 않았다. 단말에는 잘못된 DNS 서버 주소가 설정되어 있다.

#### 제공 단서

- 이름으로 접근 시 `Name resolution failed`
- IP로 접근할 수 있는 내부 DNS 서버가 토폴로지에 표시
- DNS 서버 포트와 프로토콜 설명 제공
- 올바른 질의 결과에 A 레코드와 TTL 표시

#### 해결 과정

1. 현재 DNS 설정 확인
2. 내부 DNS 서버 주소로 수정
3. A 레코드 질의
4. 반환된 IP와 TTL을 증거 노트에 저장
5. 이름을 사용해 대상 서비스 연결

#### 승리 조건

- 올바른 A 레코드 확보
- 도메인 이름을 이용해 서비스 응답 수신

#### 단계별 힌트

- H1: 포트 문제가 아니라 이름을 주소로 바꾸는 단계에서 실패했습니다.
- H2: DNS 서버 설정과 질의 대상을 분리해서 확인하세요.
- H3: 내부 DNS 서버에 `archive.training.local`의 A 레코드를 질의하세요.

#### 방지할 오개념

- DNS 서버와 웹 서버를 같은 서버라고 생각하는 것
- DNS가 항상 UDP만 사용한다고 단정하는 것

---

### Stage 7. 서버가 이해하는 요청

**주요 계층:** L7 HTTP  
**목표 시간:** 15~20분  
**학습 목표:** HTTP 메서드, 경로, Host 헤더, 상태 코드 해석

#### 상황

`ops.training.local:8080`의 관리 API에서 서버 상태를 확인해야 한다. 루트 경로는 상태 페이지로 리다이렉트하고, 상태 API는 올바른 메서드와 Host 헤더를 요구한다.

#### 제공 단서

- `GET /` → 리다이렉트 응답과 `Location: /status`
- 잘못된 Host → `404`
- `POST /status` → `405 Method Not Allowed`
- `Allow: GET`
- 정상 응답 본문은 JSON

#### 해결 과정

1. HTTP 요청 빌더에서 대상 연결 선택
2. `GET /` 요청
3. 상태 코드와 `Location` 헤더 확인
4. `Host: ops.training.local`과 `GET /status` 구성
5. JSON 응답 확인

#### 승리 조건

- 올바른 Host, 메서드, 경로로 `200 OK`
- 응답 JSON에서 서버 상태 값 확보

#### 단계별 힌트

- H1: 상태 코드만 보지 말고 응답 헤더를 확인하세요.
- H2: `Location`은 다음 요청 경로를, `Allow`는 허용 메서드를 알려줄 수 있습니다.
- H3: `Host: ops.training.local`로 `GET /status`를 보내세요.

#### 방지할 오개념

- HTTP가 URL 한 줄만 보내는 프로토콜이라고 생각하는 것
- 3xx, 4xx 응답을 모두 같은 실패로 취급하는 것

---

### Stage 8. 암호화보다 먼저 신원을 확인하라

**주요 계층:** L5~L7, TLS, HTTPS  
**목표 시간:** 15~22분  
**학습 목표:** HTTPS가 HTTP와 TLS를 결합한다는 점, 인증서 호스트명과 신뢰 관계 이해

#### 상황

플레이어가 서버 IP로 직접 HTTPS 접속해 인증서 이름 불일치 오류를 받는다. 인증서는 `secure.training.local`에 대해 발급되었다.

#### 제공 단서

- 서버 IP까지 TCP 443 연결 성공
- TLS 경고: `certificate name mismatch`
- 인증서 SAN: `secure.training.local`
- DNS에 해당 이름의 올바른 A 레코드 존재
- 인증서 유효 기간과 발급자 정보 표시

#### 해결 과정

1. 443/TCP 연결 확인
2. TLS 인증서 검사
3. IP와 인증서 호스트명 불일치 발견
4. DNS 이름으로 다시 접속
5. TLS 협상 성공 후 HTTPS 요청

#### 승리 조건

- 인증서 검증을 끄지 않고 TLS 세션 수립
- HTTPS `200 OK` 응답 수신

#### 단계별 힌트

- H1: 암호화 연결 자체는 시작되었지만 상대의 이름을 검증하지 못했습니다.
- H2: 인증서의 SAN과 요청한 호스트명을 비교하세요.
- H3: IP가 아니라 `secure.training.local`로 접속하세요.

#### 방지할 오개념

- 인증서 경고를 무시하는 것이 일반적인 해결 방법이라고 생각하는 것
- HTTPS를 단순히 “443번 포트”로만 이해하는 것

---

### Stage 9. 키가 여는 원격 셸

**주요 계층:** L7 SSH, 인증, 세션  
**목표 시간:** 18~25분  
**학습 목표:** SSH 서비스 식별, 사용자와 키 기반 인증, 원격 셸의 기본 흐름 이해

#### 상황

플레이어는 장애 서버를 복구할 권한이 있다. 임무용 사용자 `operator`와 세 개의 키 후보가 제공되며, 서버의 알려진 호스트 키 지문과 일치 여부를 먼저 확인해야 한다.

#### 제공 단서

- `22/TCP`에서 SSH 배너
- 서버 호스트 키 지문이 임무 문서에 제공
- 잘못된 사용자 → 사용자 인증 실패
- 잘못된 키 → `Permission denied (publickey)`
- 올바른 키의 메타데이터에 `operator@recovery` 표시

#### 해결 과정

1. SSH 서비스가 실행 중인 포트 확인
2. 서버 호스트 키 지문 비교
3. 사용자 `operator` 선택
4. 올바른 개인 키 선택
5. SSH 세션 수립
6. 제한된 셸에서 `status`, `logs`, `restart service` 작업 수행

#### 승리 조건

- 호스트 신원 확인
- 키 기반 인증 성공
- 서비스 로그 확인 후 지정 서비스 복구

#### 단계별 힌트

- H1: 서버의 신원과 사용자의 신원은 서로 다른 인증 단계입니다.
- H2: 먼저 호스트 키 지문을 확인한 뒤 사용자와 키의 메타데이터를 비교하세요.
- H3: 사용자 `operator`와 `operator@recovery` 키를 사용하세요.

#### 방지할 오개념

- SSH가 곧 비밀번호 입력 화면이라고 생각하는 것
- 무작위 비밀번호 대입을 정상적인 해결 전략으로 생각하는 것
- 서버 호스트 키와 사용자 개인 키를 혼동하는 것

---

### Stage 10. 전 계층 복구 작전

**주요 계층:** L1~L7 전체  
**목표 시간:** 30~45분  
**학습 목표:** 계층별 문제를 순서대로 격리하고 전체 통신 흐름을 완성

#### 상황

가상의 연구소 업데이트 서버가 오프라인 상태다. 플레이어는 훈련망에서 문제를 진단하고 HTTPS 관리 API를 통해 단기 SSH 인증서를 발급받은 뒤 서버에 접속해 서비스를 복구해야 한다.

#### 토폴로지

```text
Operator PC
  └─ Access Switch
      └─ Router
          └─ Firewall
              ├─ DNS Server
              └─ Update Server
                   ├─ HTTPS Management : 8443/TCP
                   └─ SSH Recovery    : 22/TCP
```

#### 초기 결함

1. Operator PC 인터페이스가 비활성화
2. 기본 게이트웨이 누락
3. DNS 서버가 잘못 설정됨
4. 관리 서비스가 표준 443이 아닌 8443에서 실행
5. 인증서는 `update.training.local` 이름에만 유효
6. 관리 API는 정확한 HTTP 메서드와 JSON 본문을 요구
7. 발급된 단기 SSH 인증서는 `recovery` 사용자에게만 유효

#### 해결 과정

1. L1에서 인터페이스 활성화
2. L3에서 IP와 기본 게이트웨이 확인
3. ping과 traceroute로 방화벽 앞까지 경로 검증
4. 올바른 DNS 서버 지정
5. `update.training.local` 주소 확인
6. 후보 포트에서 8443/TCP의 SYN-ACK 확인
7. TLS 인증서의 호스트명 확인
8. HTTPS 관리 API 문서와 오류 응답을 이용해 요청 수정
9. 단기 SSH 인증서 발급
10. `recovery` 사용자로 SSH 접속
11. 서비스 로그에서 잘못된 설정 발견
12. 설정 수정 후 서비스 재시작
13. 외부 검증 요청이 `200 OK`인지 확인

#### 주요 단서

- 각 계층 보기에서 하나씩만 명확한 이상 상태를 표시
- 하위 계층이 해결되면 다음 계층의 새로운 증거가 나타남
- HTTPS API의 `400` 응답 본문에 필요한 필드 형식 제공
- SSH 인증서에 사용자와 만료 시간 표시
- 서버 로그에 복구해야 할 서비스 이름 표시

#### 승리 조건

- 모든 Layer Gate 통과
- 유효한 HTTPS 세션에서 단기 인증서 발급
- SSH 복구 세션 수립
- 서비스 재시작
- 최종 상태 확인 요청 성공

#### 별점 기준

- 3성: 해답 힌트 없이, 과도한 프로브 없이 완료
- 2성: 개념 또는 행동 힌트 사용
- 1성: 전체 해답을 보고 직접 실행하여 완료

#### 최종 학습 리포트

스테이지 종료 시 패킷 하나를 선택해 다음 흐름을 재생한다.

```text
L1 링크 활성화
→ L2 게이트웨이 MAC 해석
→ L3 목적지 IP로 라우팅
→ L4 8443/TCP 연결
→ TLS 서버 신원 확인
→ HTTP API 요청
→ SSH 인증서 발급
→ 22/TCP SSH 세션
→ 원격 서비스 복구
```

## 12. 웹 게임 구현 구조

### 12.1 기술 방향

첫 버전은 React + TypeScript 웹 애플리케이션으로 만든다.

- 아웃게임과 복잡한 정보 패널: `React`
- 중앙 네트워크 게임 월드: `Phaser 3` WebGL
- 카메라·파티클·사운드·후처리: Phaser
- 상태 관리: `Zustand`
- 라우팅: `React Router`
- 스테이지 정의: JSON + Schema validation
- 진행 저장: 브라우저 로컬 저장소
- 네트워크 동작: 실제 소켓이 아닌 순수 TypeScript 시뮬레이션 엔진

React Flow는 실제 플레이 화면에 사용하지 않는다. 중앙 토폴로지는 다이어그램 편집기가 아니라 장비, 패킷, 충돌, 성공과 실패가 연출되는 게임 월드이므로 Phaser가 담당한다. React Flow는 추후 개발자용 스테이지 편집기를 만들 때만 검토한다.

네트워크 엔진은 규칙을 판정하고 `PresentationEvent`를 생성한다. Phaser는 해당 이벤트를 카메라, Tween, 파티클, 사운드와 후처리 효과로 재생한다. 애니메이션 좌표나 충돌 결과가 네트워크 정답을 결정해서는 안 된다.

게임 연출과 React–Phaser 연동의 상세 기준은 [웹 네트워크 게임 기술 구조 및 연출 설계](./web-game-architecture-and-direction-ko.md)를 따른다.

### 12.4 시뮬레이션 처리 순서

예를 들어 HTTPS 요청은 엔진 내부에서 다음과 같이 검증한다.

```text

```

```text

failureCode
educationalMessage

```

이 구조를 사용하면 UI와 게임 규칙을 분리할 수 있고, 네트워크 동작을 단위 테스트하기 쉽다.

## 13. 시뮬레이션 범위

### 13.1 MVP에서 구현할 것

- Ethernet 링크 상태
- MAC 주소와 단순 스위칭
- ARP 요청·응답과 캐시
- IPv4 주소와 `/8`~`/30` 서브넷
- 기본 게이트웨이와 정적 라우팅
- ICMP echo와 TTL 기반 경로 표현
- TCP 연결 수립과 종료의 교육용 모델
- UDP 요청·응답
- DNS A 레코드
- HTTP 요청과 대표 상태 코드
- 교육용 TLS 인증서 검증
- SSH 호스트 확인, 사용자 인증, 제한 셸
- 정적 방화벽 허용·차단 규칙

### 13.2 MVP에서 제외할 것

- 실제 패킷 캡처
- 실제 포트 스캔
- 실제 취약점 공격
- 전체 RFC 수준 TCP 재전송·혼잡 제어
- 동적 라우팅 프로토콜
- IPv6
- NAT
- DHCP
- Wi-Fi 보안
- 실제 암호 연산
- 실제 운영체제 셸
- 멀티플레이

시뮬레이션은 교육에 필요한 인과관계만 정확하게 표현하고, 모든 프로토콜을 완전 구현하려고 하지 않는다.

### 13.3 확장 캠페인 후보

- 11~15: DHCP, NAT, 방화벽, 포트 포워딩
- 16~20: VLAN, STP, 스위칭 루프
- 21~25: IPv6, Neighbor Discovery
- 26~30: HTTP 인증, 쿠키, 세션, API
- 31~35: DNS 캐시, 레코드 종류, DNSSEC 개념
- 36~40: 패킷 손실, 재전송, MTU, 단편화
- 41~45: 방어자 관점 로그 분석과 침해 대응
- 도전 모드: 제한 시간, Trace 제한, 최소 행동 수

## 14. 안전성과 윤리 원칙

이 프로젝트는 실제 공격 도구가 아니라 교육용 게임이어야 한다.

- 모든 주소와 대상은 앱 내부 가상 네트워크로 제한
- 실제 인터넷 스캔 기능 미제공
- 실제 운영체제 명령 실행 미제공
- 실제 취약점 익스플로잇 코드 미제공
- 무차별 비밀번호 대입을 정답으로 만들지 않음
- 스테이지 시작 시 허가된 훈련 환경임을 명시
- 공격 단계 뒤에 원인과 방어 방법을 함께 설명
- 후속 실습 연동이 필요하면 localhost 전용 Docker 랩과 명시적 허용 목록을 별도 모드로 설계

OWASP WebGoat처럼 의도적으로 취약한 교육 환경에서만 보안 실습을 수행한다는 원칙을 따른다.

## 15. 테스트 전략

### 15.1 시뮬레이션 단위 테스트

- 링크가 내려가 있으면 어떤 L3 요청도 전송되지 않음
- 같은 서브넷에서 목적지 ARP 해석 수행
- 다른 서브넷에서는 게이트웨이 MAC 해석 수행
- 경로가 없으면 올바른 실패 코드 반환
- 닫힌 포트와 필터링된 포트가 다른 결과 반환
- TCP 연결 전에는 HTTP 요청을 처리하지 않음
- TLS 이름 불일치 시 HTTPS 요청 차단
- SSH 사용자와 키가 모두 맞아야 세션 수립

### 15.2 스테이지 해답 테스트

각 스테이지에 자동 플레이 시나리오를 만든다.

- 공식 해답 경로로 항상 클리어 가능
- 필수 단서가 해답 전에 최소 하나 이상 노출
- 잘못된 순서에서도 앱이 멈추지 않음
- 하위 계층이 막힌 상태에서 상위 도구가 일관된 오류 반환
- 저장 후 재실행해도 월드 상태 복구

### 15.3 UI 테스트

- 1280×720에서도 주요 패널 사용 가능
- 1440×900에서 기본 레이아웃 최적화
- 확대·축소 후 노드 선택 좌표 정확
- 패킷이 많은 경우에도 프레임 저하 최소화
- 색상 외에 아이콘과 텍스트로 상태 구분
- 키보드만으로 주요 도구 접근 가능

- 한 스테이지의 원인과 해결 과정이 한 문장으로 설명 가능

- 패널 레이아웃
- Phaser 네트워크 월드와 카메라
- 장비 선택과 링크 렌더링

- Phaser 이벤트 후 React 목표와 증거가 갱신됨

### Phase 2. L1~L4 시뮬레이션 — 2주

완료 기준:

### Phase 3. L5~L7 시뮬레이션 — 1~2주

## 17. MVP 완료 기준

다음 조건을 모두 만족하면 첫 버전이 완성된 것으로 본다.

- 10개 스테이지가 처음부터 끝까지 플레이 가능
- 각 스테이지에 학습 목표, 관찰 단서, 3단계 이상 힌트가 존재
- L1부터 L7까지 최소 한 번 이상 핵심 상호작용 제공
- HTTP, HTTPS, DNS, TCP, UDP, ICMP, ARP, SSH를 게임에서 사용
- 모든 통신이 앱 내부 시뮬레이션에서 처리
- 무작위 버튼 선택만으로는 종합 스테이지 클리어 불가
- 패킷을 계층별로 펼쳐 볼 수 있음
- 공식 해답 자동 테스트가 모든 스테이지에서 통과
- 클리어 후 “왜 성공했는지” 계층별 리포트 제공
- 네트워크 지식이 없는 테스트 사용자도 힌트를 통해 첫 3개 스테이지 완료 가능

## 18. 주요 위험과 대응

| 위험 | 발생 문제 | 대응 |
|---|---|---|
| OSI를 지나치게 문자 그대로 사용 | 잘못된 지식 학습 | Layer Gate라는 교육적 추상화임을 명시 |
| 버튼이 너무 많음 | 초보자 진입 실패 | 스테이지별 도구 순차 해금 |
| 오답 피드백이 모호함 | 무작위 클릭 게임화 | 패킷·로그·실패 지점을 항상 반환 |
| 네트워크 엔진 범위 폭증 | 개발 중단 | MVP 프로토콜 동작을 교육용 최소 모델로 제한 |
| 그래프 UI 개발 과다 | 콘텐츠 부족 | 초기 노드 위치를 JSON에 고정 |
| 터미널 명령 암기 게임화 | 네트워크 학습 약화 | 명령 자동완성, 목적별 버튼과 셸 병행 |
| 해킹 기능의 오용 | 안전 문제 | 실제 네트워크·셸과 완전히 분리 |
| 스테이지 제작 비용 | 확장 지연 | 데이터 기반 StageDefinition과 검증 도구 구축 |

## 19. 개발 시작 순서

처음부터 10개 스테이지를 모두 만들지 않는다. 다음 순서가 가장 안전하다.

1. Stage 3의 IP·게이트웨이 퍼즐을 종이 또는 정적 UI로 만든다.
2. `WorldState → PlayerAction → ActionResult` 엔진 구조를 먼저 만든다.
3. Stage 1, 3, 5만 구현해 L1, L3, L4가 자연스럽게 이어지는지 검증한다.
4. 패킷 타임라인과 증거 노트를 추가한다.
5. Stage 7 HTTP와 Stage 9 SSH를 추가한다.
6. 전체 구조가 안정된 뒤 나머지 스테이지를 JSON 콘텐츠로 작성한다.
7. 마지막에 Stage 10을 조합한다.

첫 기술 프로토타입의 목표는 예쁜 화면이 아니라 다음 질문에 답하는 것이다.

> 플레이어가 오류 결과만 보고 어느 계층을 조사해야 하는지 추론할 수 있는가?

이 질문에 “그렇다”라고 답할 수 있어야 게임의 핵심이 성립한다.
