# STACK//BREACH 현재 구현 상세

> 기준일: 2026년 6월 19일  
> 기준 범위: 현재 저장소의 실제 코드  
> 구현 단계: `Stage 3: 서버 한 대의 한계` 수직 프로토타입

## 1. 현재 게임 정의

플레이어가 격자 보드에 클라우드 장비를 배치하고 장비 사이의 트래픽 경로를 직접 그려, 몰려오는 요청을 제한 시간 안에 처리하는 아키텍처 디펜스 게임이다.

현재 프로토타입의 학습 목표는 다음 두 가지다.

1. 서버를 추가하는 것만으로는 트래픽이 자동 분산되지 않는다.
2. 로드밸런서와 두 서버를 올바른 경로로 연결해야 수평 확장이 동작한다.

## 2. 한 판의 전체 흐름

### 2.1 시작

- 메인 메뉴에서 `Stage 3 시작`을 선택한다.
- 시작 코인은 40이다.
- 트래픽 입구, 앱 서버 A, 데이터베이스는 보드에 기본 배치되어 있다.
- 시작 시 장비 사이 연결은 없다.

### 2.2 첫 웨이브 준비

장비 위에서 포인터를 누르고 다른 장비 위에서 놓아 경로를 만든다.

```text
트래픽 입구 ─ 앱 서버 A ─ 데이터베이스
```

이 두 연결이 모두 있어야 단일 서버 경로가 유효하다.

### 2.3 첫 웨이브

- 이름: 첫 손님
- 요청 수: 20
- 생성 시간: 8초
- 목표 성공률: 95%
- 정상 경로가 있으면 앱 서버 A 한 대로 전부 처리할 수 있다.

통과한 요청은 코인을 지급하며, 웨이브 통과 보너스가 추가된다.

### 2.4 두 번째 웨이브

- 이름: 점심시간 폭주
- 요청 수: 50
- 생성 시간: 8초
- 목표 성공률: 90%
- 단일 서버 경로에서는 처리 슬롯과 Queue가 포화되어 실패한다.

실패하면 로드밸런서와 앱 서버 B가 해금된다. 실패해도 획득 코인과 이미 설치한 시설은 유지된다.

### 2.5 확장과 재도전

Build Dock의 장비 카드를 빈 격자 칸으로 드래그하거나, 카드를 선택한 뒤 강조된 칸을 클릭해 배치한다.

- 로드밸런서: 80 코인
- 앱 서버 B: 100 코인

두 장비를 설치한 뒤 다음 경로를 직접 완성한다.

```text
트래픽 입구
  └─ 로드밸런서
      ├─ 앱 서버 A ─ 데이터베이스
      └─ 앱 서버 B ─ 데이터베이스
```

필수 연결은 총 5개다.

1. 트래픽 입구 ↔ 로드밸런서
2. 로드밸런서 ↔ 앱 서버 A
3. 로드밸런서 ↔ 앱 서버 B
4. 앱 서버 A ↔ 데이터베이스
5. 앱 서버 B ↔ 데이터베이스

완성된 경로에서는 요청 ID를 기준으로 두 서버에 Round Robin 분산한다.

## 3. 보드와 조작

### 격자

- 크기: 9열×4행
- 고정 장비: 트래픽 입구, 앱 서버 A, 데이터베이스
- 자유 배치 장비: 로드밸런서, 앱 서버 B
- 이미 장비가 있는 칸에는 추가 배치할 수 없다.

### 장비 배치

- 카드 드래그 후 빈 격자 칸에 드롭
- 카드 선택 후 빈 격자 칸 클릭
- 웨이브 실행 중에는 배치할 수 없음
- 현재 버전은 설치 후 이동, 삭제, 환불을 지원하지 않음

### 경로 연결

- 장비에서 다른 장비까지 포인터 드래그
- 같은 두 장비를 다시 연결하면 해당 선 제거
- `그린 길 지우기`로 모든 연결 제거
- 웨이브 실행 중에는 경로를 수정할 수 없음
- 선이 시각적으로 교차해도 별도의 접점으로 처리하지 않음

## 4. 시뮬레이션 규칙

| 항목 | 현재 값 |
|---|---:|
| 시뮬레이션 Tick | 100ms |
| 서버당 동시 처리 | 2개 |
| 요청 처리 시간 | 620ms |
| 서버당 Queue 용량 | 7개 |
| 요청 제한 시간 | 3,600ms |
| 최대 시뮬레이션 시간 | 30초 |

요청 상태:

```text
Spawned
→ Routed
→ Started 또는 Queued
→ Completed / Dropped / Timed Out
```

- 처리 슬롯이 비어 있으면 요청을 즉시 처리한다.
- 슬롯이 가득 차면 Queue에 넣는다.
- Queue도 가득 차면 요청을 Drop 처리한다.
- 생성 후 3.6초를 넘기면 Timeout 처리한다.
- 완전한 경로가 없으면 모든 요청을 Drop 처리한다.

코인 계산:

```text
완료 요청 수 × 2
+ 성공 시 40
+ 실패 시 20
```

## 5. 화면과 연출

### 시각 방향

- 풍선 타워 디펜스 계열의 밝고 둥근 인상
- 크림 배경, 민트 잔디, 라벤더 로드밸런서, 하늘색 서버, 노란 DB
- 작은 장비 크기와 단순한 얼굴 표현
- AWS·Azure 같은 클라우드 서비스 아이콘의 평면 벡터 문법을 참고한 자체 아이콘
- 공식 AWS·Azure 상표 아이콘이나 브랜드 자산은 사용하지 않음

### 게임 연출

- 웨이브 시작 3·2·1 카운트다운
- 여러 색상의 트래픽 유닛 생성과 이동
- Queue 위치 이동과 처리 중 축소
- 완료 요청의 DB 이동과 화면 밖 응답
- Drop·Timeout 느낌표와 소멸
- 서버 Queue 수치와 부하에 따른 표정 변화
- 민트·주황·빨강 압력 링
- 실패 시 카메라 흔들림
- 성공 시 콘페티
- 장비 설치 Pop 효과
- Web Audio 기반 시작·성공·실패 효과음

### React UI

- 상단 Mission HUD: 스테이지, 웨이브 진행률, 처리 수, 코인, 도움말
- 하단 Build Dock: 웨이브 설명, 경로 초기화, 장비 카드, 웨이브 시작
- 결과 모달: 성공률, 평균 지연, 최대 Queue, 획득 코인, 병목 설명

## 6. 코드 구조와 책임

### React

- `App.tsx`: 전체 게임 흐름과 React–Phaser 연결
- `MainMenu.tsx`: 시작 화면
- `MissionHud.tsx`: 실시간 웨이브 정보
- `BuildDock.tsx`: 장비 구매·배치 입력과 웨이브 시작
- `HelpModal.tsx`: 조작과 시스템 역할 안내
- `ResultModal.tsx`: 웨이브 결과와 재도전 흐름

### Phaser

- `GameHost.tsx`: Phaser 인스턴스 생성과 React 콜백 연결
- `ArchitectureScene.ts`: 격자, 장비, 경로, 트래픽, 카메라와 효과
- `gameEvents.ts`: React와 Phaser 사이 이벤트 버스

### 게임 판정

- `trafficSimulation.ts`: 웨이브, 경로 유효성, Queue, Drop, Timeout, 결과 계산
- `trafficSimulation.test.ts`: 단일 서버 성공, 병목 실패, 분산 성공, 불완전 경로 검증
- `gameStore.ts`: 단계, 코인, 해금, 배치 위치, 연결 상태, 결과 보관

판정과 표현은 분리되어 있다.

```text
React 입력
→ Zustand 아키텍처 상태 갱신
→ 순수 TypeScript 시뮬레이션 실행
→ 결과 이벤트 배열 생성
→ Phaser가 이벤트를 시간순으로 재생
→ React HUD와 결과 화면 갱신
```

## 7. 현재 테스트 범위

Vitest 단위 테스트는 다음 규칙을 검증한다.

1. 단일 서버가 첫 20개 요청을 처리한다.
2. 단일 서버가 50개 폭주 웨이브에서 실패한다.
3. 로드밸런서와 서버 2대의 완성 경로가 50개 요청을 처리한다.
4. 서버 B만 추가하고 로드밸런서를 연결하지 않으면 분산되지 않는다.
5. 완전한 경로가 없으면 모든 트래픽이 실패한다.

## 8. 아직 구현되지 않은 범위

다음 내용은 다른 기획 문서에 있지만 현재 코드에는 없다.

- 장비 이동, 판매, 환불
- 장비 업그레이드와 성급 합성
- Firewall, Cache, CDN, Queue, Worker, Replica
- 서버 성능 선택과 다른 분산 알고리즘
- 유지 비용, 상점, 리롤, 플레이어 레벨
- 요청 유형, 악성 트래픽, 보스 웨이브
- 10개 캠페인과 영구 저장
- 모바일 전용 반응형 레이아웃
- BGM, 에셋 아틀라스, 별도 스프라이트 파일
- 스테이지 JSON 로더와 편집기
- E2E 자동화 테스트와 배포 설정

이 목록은 현재 구현과 향후 기획을 구분하기 위한 기준이다.
