# 트래픽 경제와 보스 요청 설계

> 문서 상태: 향후 확장 기획. 현재 코드는 완료 요청 보상과 웨이브 보너스만 구현한다.
>
> 목표: 요청을 안정적으로 처리해 돈을 벌고, 그 돈으로 서버와 네트워크 시스템을 구입·증설하며 더 어려운 트래픽을 상대하는 게임 경제 설계

10칸 상점, 플레이어 레벨 1~10, 장비 티어 확률과 동일 장비 합성은 [오토배틀러 상점·레벨·장비 합성 설계](./autobattler-shop-and-merge-design-ko.md)를 따른다.

---

## 1. 패킷은 모두 같은가

결론부터 말하면 실제 네트워크 패킷은 모두 같지 않다.

- 크기가 다를 수 있다.
- TCP, UDP, ICMP처럼 프로토콜이 다르다.
- SYN, ACK 같은 제어 정보가 다르다.
- 일부는 큰 데이터를 여러 조각으로 나누어 전달한다.
- 암호화, 헤더, 우선순위 같은 정보가 다를 수 있다.

그러나 서버 부하는 패킷의 크기만으로 결정되지 않는다.

```text
아주 작은 요청
→ 복잡한 검색
→ DB 전체 조회
→ 많은 CPU 사용
```

```text
큰 이미지 요청
→ CDN Cache Hit
→ 원본 서버는 거의 일하지 않음
```

또한 하나의 HTTP 업로드나 응답은 여러 네트워크 패킷으로 나뉠 수 있다. 반대로 작은 요청 하나가 수많은 내부 작업을 만들 수도 있다.

따라서 게임에서는 다음처럼 구분한다.

| 표현 | 게임 내부 의미 |
|---|---|
| 화면의 귀여운 패킷 캐릭터 | 하나의 사용자 요청 또는 작업 |
| 이동 중 작은 꼬리 점 | 실제 전송 조각의 시각 효과 |
| 서버 처리 비용 | 요청이 발생시키는 CPU·DB·I/O 작업량 |
| 크기 | 네트워크 대역폭과 저장소 부담 |

게임 내부 공식 명칭은 `트래픽 유닛`으로 사용한다.

사용자가 이해하기 쉬운 화면 문구는 `요청` 또는 `패킷 친구` 정도로 표현한다.

## 2. 돈은 언제 지급되는가

돈은 네트워크 패킷 한 조각이 지나갈 때마다 지급하지 않는다.

하나의 서비스 요청이 정상적으로 완료될 때 한 번 지급한다.

```text
요청 생성
→ 시스템 처리
→ 응답 반환
→ 완료 판정
→ 코인 지급
```

## 2.1 기본 보상

| 요청 | 기본 코인 | 이유 |
|---|---:|---|
| 단순 상태 조회 | 1 | 처리 비용 낮음 |
| 일반 API 조회 | 2 | Logic + DB 작업 |
| 로그인 | 3 | Auth 검증 필요 |
| 데이터 쓰기 | 4 | DB 쓰기와 안정성 필요 |
| 이미지 제공 | 2 | 크지만 CDN 처리 가능 |
| 대용량 업로드 | 6 | 대역폭·저장 비용 |
| 배치 작업 | 8 | 오래 걸리는 Worker 작업 |
| 실시간 세션 | 초당 1 | 연결을 유지하는 동안 수익 |
| 보스 요청 | 30~200 | 여러 시스템을 사용하는 특별 작업 |

실제 수치는 플레이 테스트로 조정한다.

## 2.2 품질 보너스

```text
최종 보상
= 기본 코인
× 지연 시간 보너스
× 정상 응답 보너스
× 연속 처리 보너스
```

예:

| 처리 결과 | 보상 |
|---|---:|
| 목표 시간 내 완료 | 100% |
| 매우 빠르게 완료 | 120% |
| 늦지만 Timeout 전 완료 | 60% |
| Timeout | 0 |
| 잘못된 응답 | 0 + 평판 감소 |
| 데이터 유실 | 보상 없음 + 큰 패널티 |

## 2.3 Cache와 CDN 보상

Cache나 CDN이 요청을 처리해도 정상 수익을 지급한다.

서비스는 정상적으로 응답했고, 오히려 더 적은 비용으로 처리했기 때문이다.

```text
원본 서버 처리:
수익 +2
운영 비용 -1.2
순이익 +0.8

CDN 처리:
수익 +2
운영 비용 -0.3
순이익 +1.7
```

플레이어는 단순 처리량뿐 아니라 이익률도 고려하게 된다.

## 2.4 악성 요청

악성 요청은 정상 매출을 지급하지 않는다.

- Firewall 또는 WAF에서 차단: 방어 점수 적립
- 정상 서버까지 도달: 처리 자원 손실
- 공격이 성공: 평판·안정성 패널티

공격 요청 하나마다 코인을 지급하면 공격이 많을수록 돈을 버는 이상한 구조가 된다.

대신 웨이브 종료 시 방어 성과 보너스를 제공한다.

```text
공격 차단률 95%
→ 보안 보너스 +40
```

## 2.5 재시도와 중복 요청

Retry로 생성된 요청은 추가 수익을 지급하지 않는다.

모든 요청은 `rootRequestId`를 가진다.

```text
원본 요청 A
├─ Retry A-1
├─ Retry A-2
└─ Retry A-3
```

하나라도 성공하면 원본 요청 A에 대해서만 한 번 보상한다.

이렇게 해야 플레이어가 일부러 오류와 Retry를 만들어 돈을 버는 것을 막을 수 있다.

## 2.6 Queue 작업 보상

비동기 요청은 두 번에 나누어 지급할 수 있다.

```text
Queue 접수 성공: 30%
Worker 최종 완료: 70%
```

Queue에 넣기만 하고 Worker를 설치하지 않는 플레이를 방지한다.

## 3. 스테이지 내 경제 흐름

## 3.1 시작 자금

각 스테이지는 최소 구조를 만들 수 있는 시작 코인을 제공한다.

예:

```text
Stage 3 시작 자금: 300

몽글이 서버: 120
Load Balancer: 100
경로 연결: 무료
남은 자금: 80
```

## 3.2 요청 처리 수익

웨이브가 진행되는 동안 요청 위에 작은 코인 효과가 나타난다.

- 완료된 요청이 출구에 도착
- `+2` 코인이 위로 통통 떠오름
- 빠른 연속 완료 시 코인이 합쳐져 표시
- 실제 지갑 수치는 즉시 증가

요청이 너무 많을 때 모든 `+1` 텍스트를 표시하면 화면이 복잡해진다.

```text
가까이 보기: 요청별 +1
기본 보기: 1초 단위 +18 묶음 표시
```

보상 계산 자체는 요청별로 유지한다.

## 3.3 웨이브 사이 구매

초반 캠페인은 웨이브 중 구매를 제한한다.

```text
웨이브
→ 처리 수익 획득
→ 정비 시간
→ 서버·시설 구입
→ 다음 웨이브
```

중반 이후 긴 웨이브에서는 긴급 구매가 열린다.

- 비용 20% 증가
- 설치 시간 필요
- 설치 중에는 처리하지 못함

## 3.4 유지 비용

시설을 많이 설치하면 웨이브 종료 시 유지비가 발생한다.

| 시설 | 유지비 성격 |
|---|---|
| Logic Server | CPU·메모리 |
| Load Balancer | 처리량 기준 |
| CDN | 전송량 기준 |
| Cache | 메모리 용량 기준 |
| DB Replica | 항상 높은 고정 비용 |
| Serverless | 요청당 비용 |

비싼 시설을 무조건 많이 배치하는 방식이 정답이 되지 않게 한다.

## 3.5 철거와 환불

- 웨이브 전 철거: 80% 환불
- 웨이브 중 긴급 철거: 50% 환불
- OFF된 서버 철거: 40% 환불
- 튜토리얼 첫 설치 실수: 100% 환불

## 4. 돈으로 장비를 해금하는 방식

해금은 두 단계로 구분한다.

## 4.1 카탈로그 해금

캠페인 진행으로 새로운 장비 종류가 상점에 등록된다.

```text
Stage 3 진입
→ Load Balancer 카탈로그 해금
```

## 4.2 실제 구매

해금된 장비를 현재 스테이지의 요청 수익으로 구매한다.

```text
Load Balancer 해금 상태
가격 100
현재 코인 72
→ 아직 설치 불가

요청 14개 추가 처리
현재 코인 100
→ 구매 가능
```

이 구조가 사용자가 말한 “패킷을 처리해 돈을 벌고 장비를 산다”에 해당한다.

## 4.3 웨이브 수익으로 자연스럽게 해금

필수 신규 장비는 직전 웨이브를 최소 성적으로 완료해도 살 수 있어야 한다.

예:

```text
Load Balancer 가격: 100
Wave 1 최소 보장 수익: 120
```

플레이어가 초반 실수로 필수 장비를 살 수 없는 소프트락에 빠지지 않게 한다.

## 4.4 상점 티어

| 티어 | 해금 기준 | 예시 |
|---|---|---|
| Tier 1 | 기본 | 몽글이, CPU, Core |
| Tier 2 | 누적 매출 300 | 문어, Load Balancer |
| Tier 3 | 누적 매출 900 | Cache, Connection Pool |
| Tier 4 | 누적 매출 2,000 | CDN, Queue, Worker |
| Tier 5 | 캠페인 후반 | Auto Scaling, Multi-Zone |

누적 매출은 현재 스테이지 안에서만 사용하거나 캠페인 회사 성장 수치로 사용할 수 있다.

권장 방식:

- 필수 시설: 스테이지 진행으로 해금
- 선택 시설: 별·연구 포인트로 카탈로그 해금
- 실제 설치: 현재 스테이지 코인으로 구매

## 5. 로드가 높은 요청은 무엇인가

요청의 어려움은 여러 축으로 나눈다.

| 부하 축 | 영향을 받는 시스템 |
|---|---|
| 큰 데이터 크기 | 네트워크, CDN, Storage |
| 높은 CPU 작업량 | Compute Server |
| 높은 메모리 사용 | Memory Server |
| 긴 처리 시간 | Logic Slot, Queue |
| 많은 DB 조회 | Cache, DB, Replica |
| DB 쓰기 | Primary DB |
| 긴 연결 시간 | Realtime Server, L4 LB |
| 많은 하위 호출 | Microservices, Circuit Breaker |
| 짧은 마감 시간 | 저지연 서버 |
| 반복 요청 | Cache, CDN |

따라서 “큰 패킷”이 무조건 강한 보스는 아니다.

작고 가벼워 보이는 요청도 서버 내부에서 매우 무거운 작업을 만들 수 있다.

---

## 6. 보스는 단일 패킷보다 보스 요청이다

보스는 화면에서 하나의 큰 캐릭터로 보일 수 있다.

하지만 내부적으로는 다음 중 하나다.

- 하나의 매우 무거운 요청
- 여러 요청이 결합된 작업
- 특정 트래픽 패턴
- 시스템 장애를 유발하는 이벤트
- 처리 중 여러 하위 요청을 생성하는 요청

권장 명칭:

- 보스 요청
- 보스 트래픽
- 보스 이벤트

게임 화면에서는 간단히 `보스 패킷`이라고 불러도 되지만 도움말에서 실제 의미를 알려 준다.

---

## 7. 보스 요청 종류

## 7.1 대용량 업로드 고래

**외형:** 큰 파란 고래와 여러 데이터 상자  
**현실 개념:** Large Upload / Large Payload

### 특징

- 이동 속도가 느림
- 네트워크 대역폭을 오래 점유
- Logic Server가 직접 받으면 슬롯을 오래 사용
- 저장소 용량 필요

### 대응

- 업로드 전용 경로
- Object Storage
- Storage Server 두더지
- 파일 크기 제한
- 대역폭 업그레이드

### 보상

완료 시 높은 코인 지급.

### 자연스러운 학습

큰 데이터는 CPU보다 네트워크와 저장소를 먼저 막을 수 있다.

---

## 7.2 무거운 쿼리 골렘

**외형:** 작지만 바위 몸을 가진 요청  
**현실 개념:** Expensive Query / Full Scan

### 특징

- 네트워크 크기는 작음
- DB에서 매우 오래 처리
- DB Queue를 빠르게 증가
- 같은 쿼리가 반복될 수 있음

### 대응

- Database Index
- Cache
- Read Replica
- Query Timeout

### 보상

일반 조회보다 높은 코인.

### 자연스러운 학습

작은 요청이라도 내부 작업량은 클 수 있다.

---

## 7.3 캐시 파괴 카멜레온

**외형:** 지나갈 때마다 문양과 색이 조금씩 변함  
**현실 개념:** Cache Buster / Cache Key Explosion

### 특징

- 비슷한 요청이지만 Cache Key가 전부 다름
- Cache Hit가 거의 발생하지 않음
- Cache 용량을 빠르게 채움
- 원본 서버와 DB까지 모두 통과

### 대응

- Cache Key 정규화
- 불필요한 Query Parameter 제거
- WAF 규칙
- Rate Limiter

### 자연스러운 학습

Cache가 있다고 모든 반복 요청이 자동으로 빨라지는 것은 아니다.

---

## 7.4 천둥 무리

**외형:** 하나의 구름 보스가 수십 개 요청을 동시에 떨어뜨림  
**현실 개념:** Thundering Herd / Cache Stampede

### 특징

- 인기 Cache 항목이 만료되는 순간 발생
- 같은 조회 요청이 동시에 원본으로 몰림
- Cache와 DB가 갑자기 과부하

### 대응

- Cache TTL 분산
- 요청 병합
- 오래된 응답 임시 제공
- Origin Shield
- 서버 여유 용량

### 보상

구름을 구성하는 원본 요청마다 정상 수익 지급.

### 자연스러운 학습

평균 트래픽이 낮아도 같은 순간에 몰리면 장애가 날 수 있다.

---

## 7.5 재시도 히드라

**외형:** 실패할 때마다 머리가 늘어나는 용  
**현실 개념:** Retry Storm

### 특징

- 실패하면 요청 두 개를 추가 생성
- 서버가 느려질수록 더 많은 Retry 발생
- 잠시 후 원래 트래픽보다 Retry가 많아짐

### 대응

- Retry 횟수 제한
- Exponential Backoff
- Jitter
- Circuit Breaker
- 빠른 실패

### 보상

원본 요청에 대해서만 한 번 지급.

### 자연스러운 학습

재시도는 신뢰성을 높이기도 하지만 과부하 상황에서는 장애를 키울 수 있다.

---

## 7.6 느린 연결 문어

**외형:** 긴 촉수로 서버 슬롯을 붙잡음  
**현실 개념:** Slow Client / Long-held Connection

### 특징

- 작업량은 낮지만 연결 슬롯을 오래 점유
- 새로운 요청이 들어올 슬롯이 부족해짐
- 일반 CPU 업그레이드는 효과가 작음

### 대응

- Connection Timeout
- L4 Load Balancer
- 해파리 I/O Server
- 연결 수 업그레이드
- Rate Limit

### 자연스러운 학습

서버 부하는 계산량뿐 아니라 연결 유지 시간에서도 발생한다.

---

## 7.7 핫키 용암 슬라임

**외형:** 같은 열쇠 문양을 가진 뜨거운 유닛 무리  
**현실 개념:** Hot Key / Hot Partition

### 특징

- 모든 요청이 같은 Cache Key 또는 DB 파티션으로 이동
- 전체 서버 용량은 남지만 특정 경로만 과부하
- 단순 서버 추가로 해결되지 않을 수 있음

### 대응

- Hot Key 복제
- Local Cache
- Sharding Key 변경
- 요청 분산

### 자연스러운 학습

전체 평균이 정상이어도 한 데이터에 요청이 몰리면 병목이 생긴다.

---

## 7.8 팬아웃 마법사

**외형:** 서버에 도착하면 작은 하위 요청을 여러 개 소환  
**현실 개념:** Fan-out Request / Downstream Dependency

### 특징

- 요청 하나가 DB, 검색, 결제, 추천 서버 호출을 생성
- 하위 시스템 하나가 느리면 전체 응답 지연
- 처리 비용이 눈덩이처럼 증가

### 대응

- Cache
- 비동기 분리
- Timeout
- Circuit Breaker
- Bulkhead

### 자연스러운 학습

요청 하나가 내부에서는 많은 시스템을 사용할 수 있다.

---

## 7.9 독성 메시지 유령

**외형:** Queue에서 계속 되돌아오는 보라색 유령  
**현실 개념:** Poison Message

### 특징

- Worker가 처리할 때마다 실패
- Queue로 다시 돌아감
- Worker 슬롯을 계속 낭비
- 정상 작업의 처리를 방해

### 대응

- 최대 재시도 횟수
- Dead Letter Queue
- 실패 유형별 Worker

### 자연스러운 학습

처리할 수 없는 작업은 정상 Queue에서 분리해야 한다.

---

## 7.10 트랜잭션 기사

**외형:** 여러 개의 잠금 방패를 가진 기사  
**현실 개념:** Multi-step Transaction / Write-heavy Operation

### 특징

- 재고, 결제, 주문 DB를 순서대로 처리
- 중간에 실패하면 이전 작업을 되돌려야 함
- DB 쓰기 잠금을 오래 점유

### 대응

- 빠른 Primary DB
- Connection Pool
- Queue
- Idempotency
- 작업 분리

### 보상

높은 수익을 주지만 데이터 불일치 시 큰 패널티.

### 자연스러운 학습

모든 쓰기 작업을 단순 조회처럼 분산할 수 있는 것은 아니다.

---

## 7.11 콜드 스타트 눈사람

**외형:** 등장할 때 얼어 있다가 천천히 녹는 구름 서버  
**현실 개념:** Serverless Cold Start

### 특징

- Serverless 처리 유닛이 처음 생성될 때 지연 발생
- 갑작스러운 대량 요청에서 여러 Cold Start 동시 발생

### 대응

- Provisioned Concurrency
- 최소 인스턴스 유지
- Warm-up
- 일반 서버와 혼합

### 자연스러운 학습

자동 확장은 즉시 무료로 생기는 능력이 아니다.

---

## 7.12 대역폭 괴수

**외형:** 경로 전체를 차지하는 긴 미디어 용  
**현실 개념:** Large Download / Streaming Burst

### 특징

- 서버 처리보다 네트워크 경로를 오래 점유
- 뒤따르는 작은 요청까지 느려짐
- 원본 전송 비용 증가

### 대응

- CDN
- 압축
- 품질 단계 조절
- 전용 미디어 경로

### 자연스러운 학습

서버 CPU가 멀쩡해도 네트워크 대역폭이 병목이 될 수 있다.

---

## 8. 보스 웨이브 종류

보스 하나만 등장시키는 방식 외에 패턴형 보스도 사용한다.

## 단일 거대형

- 대용량 업로드 고래
- 무거운 쿼리 골렘
- 트랜잭션 기사

한 유닛을 끝까지 처리하면 클리어.

## 증식형

- 재시도 히드라
- 팬아웃 마법사
- 독성 메시지 유령

처리 방식이 잘못되면 수가 늘어난다.

## 군집형

- 천둥 무리
- 핫키 슬라임
- DDoS 떼

하나의 보스 캐릭터가 트래픽 무리를 생성한다.

## 점유형

- 느린 연결 문어
- 대역폭 괴수

처리 슬롯이나 경로를 오랫동안 붙잡는다.

---

## 9. 보스와 시스템 해금 연결

| 보스 | 처음 등장 | 핵심 대응 | 해금 |
|---|---:|---|---|
| 무거운 쿼리 골렘 | Stage 4 | Cache, Index | DB Index |
| 대용량 업로드 고래 | Stage 5 | Object Storage | 두더지 |
| 천둥 무리 | Stage 5 | CDN, Origin Shield | TTL 분산 |
| 트랜잭션 기사 | Stage 6 | Primary DB, Pool | Idempotency |
| 독성 메시지 유령 | Stage 7 | DLQ | Dead Letter Queue |
| 캐시 파괴 카멜레온 | Stage 8 | WAF, Key 정규화 | Custom Rule |
| 느린 연결 문어 | Stage 9 | Timeout, I/O Server | 해파리 |
| 재시도 히드라 | Stage 9 | Circuit Breaker | Backoff/Jitter |
| 팬아웃 마법사 | Stage 9 | Timeout, Bulkhead | Bulkhead |
| 대역폭 괴수 | Stage 10 | CDN, 압축 | 미디어 Edge |
| 콜드 스타트 눈사람 | Stage 10 | Warm Pool | Provisioned Capacity |
| 핫키 슬라임 | Challenge | 분산·복제 | Advanced Sharding |

## 10. 스테이지별 경제 예시

## Stage 1

```text
시작 코인: 0
단순 요청 보상: +2
웨이브 총 요청: 40
예상 수익: 80

Wave 1 종료
→ CPU 업그레이드 가격 60
```

처리 수익으로 첫 업그레이드를 구매한다.

## Stage 3

```text
Wave 1 예상 수익: 160

추가 몽글이: 100
Load Balancer: 80
```

최소 성공 수익으로 둘 중 하나만 먼저 구매할 수 있다.

다음 작은 웨이브를 처리해 나머지 시설을 산다.

플레이어는 즉시 완성 구조를 받지 않고 운영 수익으로 확장한다.

## Stage 5

```text
이미지 요청 보상: +3
원본 처리 비용: -2
CDN 처리 비용: -0.5

원본 순이익: +1
CDN 순이익: +2.5
```

CDN은 처리량뿐 아니라 수익성을 높인다.

## Stage 7

```text
Queue 접수: +2
Worker 완료: +5
실패 후 DLQ 격리: 방어 보너스
```

## 11. 경제적 선택

## 싼 서버 여러 대

- 초기 비용 낮음
- Load Balancer 필요
- 유지비 증가
- 장애에 강함

## 비싼 서버 한 대

- 설치가 단순
- 높은 처리 속도
- OFF 시 전체 중단
- 수직 확장 가격 급증

## CDN

- 비싼 초기 비용
- 정적 요청당 높은 순이익
- 동적 요청에는 효과 없음

## Cache

- 저렴하게 DB 부하 감소
- 데이터가 자주 바뀌면 효율 낮음

## Auto Scaling

- 평상시 비용 절감
- Burst 시작 직후에는 늦을 수 있음
- 사용한 시간만큼 비용 발생

## Serverless

- 설치 비용 거의 없음
- 요청당 비용
- 지속 트래픽에서는 비쌀 수 있음

---

## 12. 실패해도 다시 성장할 수 있게 하는 장치

처리 실패가 많으면 돈을 못 벌고, 돈이 없어서 시설을 못 사는 악순환이 생길 수 있다.

이를 막기 위해 다음을 사용한다.

## 최소 운영 보조금

웨이브 종료 시 필수 시설 구매에 필요한 최소 금액을 보장한다.

## 실패 분석 보상

처음 발견한 병목은 분석 포인트를 지급한다.

```text
첫 DB 연결 고갈 발견
→ +20 분석 보상
```

## 재도전 할인

같은 웨이브 재도전 시 이번에 처음 해금된 필수 시설 가격 20% 감소.

## 소프트락 방지

- 필수 시설 판매 불가
- 최소 한 개 서버는 유지
- 잘못 설치한 신규 시설은 첫 회 100% 환불

---

## 13. 보스 처리 연출

## 등장

- 배경 음악이 살짝 바뀜
- 보스 유닛은 일반 요청보다 2~4배 큼
- 등장 전에 다음 부하 축만 아이콘으로 예고

예:

```text
CPU 아이콘 ×3
DB 아이콘 ×5
Deadline 20초
```

시스템 이름이나 정답은 알려 주지 않는다.

## 처리 중

- 보스 몸체가 여러 처리 단계로 나뉨
- 사용 중인 시스템 아이콘이 몸체에 붙음
- 처리할수록 체력 대신 `남은 작업량` 게이지 감소
- 병목 시설에서 보스가 멈추고 해당 시설의 압력 링이 빠르게 증가

## 성공

- 작업량 게이지가 0
- 보스가 완료 응답 또는 보상 상자로 변함
- 높은 코인 지급
- 현실 개념 카드 해금

## 실패

- Deadline이 0
- 보스가 Retry나 하위 요청으로 분열할 수 있음
- 무조건 즉시 게임 오버가 아니라 다음 장애 패턴으로 이어짐

---

## 14. 추천 첫 보스

첫 프로토타입 보스는 `무거운 쿼리 골렘`이 적합하다.

이유:

- 크기는 작지만 작업량이 크다는 차이를 보여 줌
- Logic Server와 DB 병목을 동시에 보여 줄 수 있음
- Cache와 DB Index 해금으로 자연스럽게 연결
- 공격 트래픽이 아니므로 게임의 기본 처리 개념에 집중 가능

## 프로토타입 패턴

```text
일반 요청 20개
→ 서버가 안정적으로 처리

무거운 쿼리 골렘 등장
→ 서버 처리
→ DB에서 오래 정지
→ DB 압력 링 증가

실패 또는 매우 느린 완료
→ Index 해금

재도전
→ 처리 시간이 크게 감소
→ 높은 코인 보상
```

두 번째 보스는 `재시도 히드라`가 적합하다.

시스템 장애가 왜 요청량을 더 증가시키는지 강하게 보여 줄 수 있다.

---

## 15. 최종 권장 규칙

1. 화면의 패킷 캐릭터 하나는 하나의 서비스 요청을 의미한다.
2. 실제 네트워크 조각 수로 돈을 계산하지 않는다.
3. 정상 완료된 원본 요청에 한 번만 코인을 지급한다.
4. Cache와 CDN 완료도 정상 수익을 지급한다.
5. 악성 요청은 매출이 아니라 웨이브 방어 보너스를 준다.
6. Retry와 중복 요청은 추가 수익을 주지 않는다.
7. 요청은 크기, CPU, DB, 연결 시간 등 서로 다른 부하를 가진다.
8. 보스는 단일 패킷이 아니라 무거운 요청 또는 트래픽 패턴이다.
9. 보스의 약점은 특정 서버 캐릭터와 아키텍처 조합으로 만든다.
10. 필수 장비를 살 수 없는 소프트락을 경제 설계에서 방지한다.
