# STACK//BREACH 캠페인 1: 네트워크 스테이지 10개 구상안

> 문서 상태: 이전 네트워크 침투 퍼즐 캠페인 보관안. 현재 아키텍처 디펜스 캠페인과는 별개다.

## 캠페인 개요

가상 도시의 핵심 네트워크 `NEXUS`가 정체불명의 오류 코드 `NULL`에 의해 계층별로 차단되었다. 플레이어는 훈련용 사이버 대응 요원으로 투입되어 각 구역의 통신을 복구하고, 마지막에는 중앙 서버에 접근해 `NULL`의 실행을 중단해야 한다.

각 스테이지는 하나의 네트워크 개념을 중심으로 하지만, 플레이 방식은 객관식 퀴즈가 아니다.

```text
현상 관찰
→ 장비와 패킷 조사
→ 문제 계층 추정
→ 도구 선택과 값 설정
→ 패킷 발사
→ 실패 지점 분석
→ 네트워크 상태 수정
→ 서비스 접근
→ 복구 완료
```

---

## 전체 진행 구조

| Stage | 임무명 | 핵심 개념 | 새로 해금되는 조작 | 최종 목표 |
|---:|---|---|---|---|
| 1 | 끊어진 첫 신호 | L1, 링크, 인터페이스 | 링크 검사, 인터페이스 활성화 | 감시 단말 연결 |
| 2 | 응답 없는 주소 | Ethernet, MAC, ARP | ARP 요청, 프레임 분석 | 같은 LAN의 서버 식별 |
| 3 | 경계 밖의 목적지 | IP, 서브넷, 게이트웨이 | IP 설정, 서브넷 분석 | 다른 네트워크 진입 |
| 4 | 사라지는 패킷 | ICMP, TTL, 라우팅 | ping, traceroute, 정적 경로 | 끊긴 중간 경로 복구 |
| 5 | 닫힌 문과 열린 문 | TCP, UDP, 포트 | TCP Probe, 핸드셰이크 | 실제 서비스 포트 발견 |
| 6 | 이름을 잃은 서버 | DNS, 이름 해석 | DNS Query, 캐시 분석 | 숨겨진 서버 주소 확보 |
| 7 | 서버의 언어 | HTTP | HTTP Request Builder | 관리 API 호출 |
| 8 | 믿을 수 없는 얼굴 | TLS, HTTPS, 인증서 | TLS Inspector | 서버 신원 검증 |
| 9 | 잠긴 원격 셸 | SSH, 키 인증, 세션 | SSH Client, 제한 셸 | 서버 내부 복구 |
| 10 | FULL STACK BREACH | L1~L7 종합 | 모든 도구와 특수 스킬 | 중앙 서버 복구 |

# Stage 1. 끊어진 첫 신호

## 핵심 정보

| 항목 | 내용 |
|---|---|
| 주요 계층 | L1 물리 계층 |
| 예상 시간 | 5~8분 |
| 난이도 | 튜토리얼 |
| 핵심 개념 | 전원, NIC, 케이블, 링크 상태 |
| 새 도구 | Link Tester, Interface Control |

## 임무 브리핑

도시 외곽의 감시 기지가 완전히 침묵했다. 감시 서버가 공격받은 것처럼 보이지만, 플레이어 단말에서는 어떠한 패킷도 출발하지 않는다.

목표는 감시 카메라 서버에 접근해 생존 신호를 확인하는 것이다.

## 토폴로지

```text
Operator PC ─── Access Switch ─── Camera Server
```

## 숨겨진 문제

- Operator PC의 `eth0` 인터페이스가 비활성화되어 있다.
- 예비 인터페이스 `eth1`은 케이블이 연결되지 않았다.
- 서버와 스위치는 정상이다.

## 플레이 흐름

1. HTTP 접근을 시도하지만 패킷이 생성되지 않는다.
2. 플레이어 단말의 링크 LED가 꺼져 있음을 발견한다.
3. L1 보기로 전환한다.
4. `eth0`과 `eth1`의 연결 상태를 비교한다.
5. 케이블이 연결된 `eth0`을 활성화한다.
6. 스위치 포트와 단말 포트가 점등된다.
7. 자동 상태 확인 패킷이 서버까지 왕복한다.

## 플레이어가 얻는 단서

- `eth0: ADMIN DOWN`
- `eth1: NO CABLE`
- 스위치 1번 포트: `NO LINK`
- 상위 계층 도구: `Network interface unavailable`

## 잘못된 행동과 반응

| 행동 | 게임 반응 |
|---|---|
| 서버를 반복 클릭 | 서버가 아니라 출발 단말이 붉게 점멸 |
| `eth1` 활성화 | 포트는 켜지지만 케이블 끝에서 신호 소멸 |
| HTTP 반복 실행 | 패킷 조립이 시작되기 전에 `L1 BLOCKED` 표시 |

## 클리어 연출

단말에서 발생한 전기 펄스가 케이블과 스위치를 지나 서버까지 전달된다. 네트워크 전체가 청록색으로 점등되고 `LINK ESTABLISHED`가 표시된다.

## 선택 과제

- 잘못된 인터페이스를 활성화하지 않고 완료
- HTTP 재시도 1회 이하

## 이 스테이지가 가르치는 것

서버나 프로토콜을 조사하기 전에 내 장비에서 패킷을 보낼 수 있는지 먼저 확인해야 한다.

# Stage 2. 응답 없는 주소

## 핵심 정보

| 항목 | 내용 |
|---|---|
| 주요 계층 | L2 데이터 링크 |
| 예상 시간 | 8~12분 |
| 난이도 | 쉬움 |
| 핵심 개념 | Ethernet, MAC 주소, ARP, 브로드캐스트 |
| 새 도구 | ARP Pulse, ARP Cache, Frame Inspector |

## 임무 브리핑

같은 시설 내부에 데이터 보관 서버가 존재한다. 서버 IP는 확보했지만 Operator PC는 프레임을 누구에게 보내야 할지 알지 못한다.

같은 LAN에 프린터와 미끼 장비도 있어 IP만 보고 장비를 선택할 수 없다.

## 토폴로지

```text
                 ┌─ Archive Server
Operator PC ─ Switch
                 ├─ Printer
                 └─ Decoy Terminal
```

## 숨겨진 문제

- ARP 캐시가 비어 있다.
- Archive Server의 IP는 `192.168.10.20`이다.
- 플레이어는 목적지 MAC 주소를 아직 모른다.

## 플레이 흐름

1. 대상 IP `192.168.10.20`을 증거 노트에서 확인한다.
2. ARP 캐시가 비어 있음을 확인한다.
3. `ARP Pulse`로 해당 IP의 소유자를 묻는다.
4. 노란 브로드캐스트 링이 같은 LAN 전체로 퍼진다.
5. Archive Server만 ARP Reply를 반환한다.
6. IP와 MAC의 매핑을 캐시에 저장한다.
7. 목적지 MAC이 포함된 Ethernet 프레임을 전송한다.

## 핵심 퍼즐

플레이어는 장비 아이콘을 보고 서버를 고르는 것이 아니라, ARP 응답을 통해 IP와 MAC의 관계를 확보해야 한다.

## 플레이어가 얻는 단서

- `Who has 192.168.10.20?`
- `192.168.10.20 is at 02:42:AC:10:00:14`
- 스위치 MAC 테이블의 포트 정보
- 응답 프레임의 Source MAC

## 잘못된 행동과 반응

| 행동 | 게임 반응 |
|---|---|
| 프린터 MAC 직접 선택 | 프레임이 프린터로 전달된 뒤 `SERVICE MISMATCH` |
| 다른 서브넷에 ARP 시도 | 브로드캐스트가 라우터에서 더 이상 진행되지 않음 |
| 임의 MAC 입력 | 스위치가 목적지를 찾지 못해 프레임을 플러딩 |

## 클리어 연출

ARP 응답이 돌아오며 IP 문자와 MAC 문자가 하나의 카드로 결합된다. 이후 프레임이 정확한 스위치 포트로 이동하고 `ADDRESS RESOLVED`가 표시된다.

## 선택 과제

- ARP 요청 1회로 서버 발견
- 프레임 인스펙터에서 Source MAC과 Destination MAC을 정확히 지목

## 이 스테이지가 가르치는 것

같은 LAN에서 IPv4 패킷을 보내려면 목적지 또는 다음 홉의 링크 계층 주소가 필요하다.

# Stage 3. 경계 밖의 목적지

## 핵심 정보

| 항목 | 내용 |
|---|---|
| 주요 계층 | L3 네트워크 계층 |
| 예상 시간 | 10~15분 |
| 난이도 | 쉬움 |
| 핵심 개념 | IP, 서브넷 마스크, 네트워크 주소, 기본 게이트웨이 |
| 새 도구 | IP Config, Subnet Lens, Route Table |

## 임무 브리핑

다음 데이터 조각은 다른 구역의 인증 서버에 있다. 주소는 비슷해 보이지만 직접 프레임을 전송하면 아무 장비도 응답하지 않는다.

## 토폴로지

```text
10.0.10.50/24                 10.0.20.15/24
Operator PC ─ Switch ─ Router ─ Switch ─ Auth Server
                       10.0.10.1
```

## 숨겨진 문제

- Operator PC에 기본 게이트웨이가 없다.
- 출발지는 `10.0.10.0/24`, 목적지는 `10.0.20.0/24`에 속한다.
- 플레이어가 목적지 서버의 MAC을 직접 찾으려고 하면 실패한다.

## 플레이 흐름

1. 목적지로 ARP를 시도하지만 응답이 없음을 확인한다.
2. `Subnet Lens`로 두 주소의 네트워크 부분을 비교한다.
3. 두 장비가 다른 서브넷에 있음을 발견한다.
4. Route Table에서 원격 네트워크 경로가 없음을 확인한다.
5. `10.0.10.1`을 기본 게이트웨이로 지정한다.
6. 게이트웨이의 MAC 주소를 ARP로 찾는다.
7. IP 목적지는 서버로 유지하면서 Ethernet 목적지를 게이트웨이로 설정한다.
8. 라우터가 패킷을 목적지 네트워크로 전달한다.

## 핵심 퍼즐

패킷의 최종 IP 목적지는 원격 서버지만 첫 프레임의 목적지 MAC은 게이트웨이의 MAC이라는 점을 시각적으로 이해하게 한다.

## 플레이어가 얻는 단서

- `Destination is outside local /24`
- Route Table: `10.0.10.0/24 only`
- Router LAN Interface: `10.0.10.1`
- 원격 서버 대상 ARP 요청에 응답 없음

## 잘못된 행동과 반응

| 행동 | 게임 반응 |
|---|---|
| 원격 서버 MAC을 ARP로 반복 조사 | ARP 링이 라우터 앞에서 차단 |
| 목적지 서버를 게이트웨이로 설정 | 로컬에서 다음 홉을 찾지 못함 |
| 서브넷 마스크를 임의 변경 | 로컬이라고 잘못 판단한 패킷이 LAN에서 방황 |

## 클리어 연출

Operator PC와 서버 영역 사이에 있던 경계선이 열리고 라우터가 회전하며 두 네트워크를 연결한다. `GATEWAY ACQUIRED`가 표시된다.

## 선택 과제

- 잘못된 서브넷 설정 없이 완료
- 첫 Ethernet 프레임의 목적지 MAC을 정확히 분석

## 이 스테이지가 가르치는 것

다른 네트워크에 있는 목적지는 직접 찾는 것이 아니라 라우터를 다음 홉으로 사용한다.

# Stage 4. 사라지는 패킷

## 핵심 정보

| 항목 | 내용 |
|---|---|
| 주요 계층 | L3, ICMP, 라우팅 |
| 예상 시간 | 12~18분 |
| 난이도 | 보통 |
| 핵심 개념 | ping, traceroute, TTL, 라우팅 테이블 |
| 새 도구 | Ping Shot, Route Pulse, Static Route |

## 임무 브리핑

백업 데이터 센터까지의 경로가 끊겼다. 목적지 서버는 살아 있다는 외부 보고가 있지만 Operator PC의 패킷은 중간 네트워크에서 사라진다.

## 토폴로지

```text
Operator ─ R1 ─ R2 ─ R3 ─ Backup Server
                         172.16.30.20
```

## 숨겨진 문제

- R2에 `172.16.30.0/24` 경로가 없다.
- R1과 R3, 서버는 정상이다.
- ping만 사용하면 단순 시간 초과만 보인다.

## 플레이 흐름

1. ping을 보내 목적지 응답이 없음을 확인한다.
2. `Route Pulse`를 실행한다.
3. TTL 1 패킷이 R1에서 소멸하고 ICMP 응답을 반환한다.
4. TTL 2 패킷이 R2에서 소멸하고 응답한다.
5. 다음 패킷이 R2를 넘지 못한다.
6. 카메라가 마지막 응답 장비 R2를 강조한다.
7. R2의 Route Table을 조사한다.
8. 목적지 네트워크 경로가 없음을 발견한다.
9. R3를 다음 홉으로 하는 정적 경로를 추가한다.
10. traceroute와 ping을 다시 실행해 복구를 검증한다.

## 핵심 퍼즐

목적지 서버를 계속 조사하는 대신 마지막으로 패킷이 정상 도달한 중간 장비를 찾아야 한다.

## 플레이어가 얻는 단서

- ping: `Request timed out`
- traceroute 마지막 응답: R2
- R2 로그: `No matching route for 172.16.30.20`
- R2와 R3 사이의 연결 주소

## 잘못된 행동과 반응

| 행동 | 게임 반응 |
|---|---|
| 서버를 재부팅하려고 시도 | 접근 경로가 없어 명령 전달 실패 |
| R1 경로 변경 | 기존 정상 경로가 흔들리고 Trace 증가 |
| 잘못된 다음 홉 입력 | 패킷이 이전 라우터로 돌아가며 루프 경고 |

## 클리어 연출

어둡게 끊겨 있던 R2와 R3 사이의 경로가 빛나고, 패킷이 모든 홉을 연속 통과한다. 카메라가 패킷을 따라 서버까지 이동하며 `ROUTE RESTORED`가 표시된다.

## 선택 과제

- ping 1회, traceroute 1회만 사용
- 라우팅 루프 없이 완료
- 변경 전후 경로 비교

## 이 스테이지가 가르치는 것

통신 실패는 목적지 문제만이 아니며, 중간 경로를 단계적으로 조사해야 한다.

# Stage 5. 닫힌 문과 열린 문

## 핵심 정보

| 항목 | 내용 |
|---|---|
| 주요 계층 | L4 전송 계층 |
| 예상 시간 | 15~20분 |
| 난이도 | 보통 |
| 핵심 개념 | TCP, UDP, 포트, 3-way handshake, RST |
| 새 도구 | TCP Needle, Handshake View, UDP Probe |

## 임무 브리핑

노드의 IP 주소까지는 정상적으로 도달하지만 관리 화면을 열 수 없다. 서버에는 여러 서비스가 실행 중이며 무작위 포트 조사는 보안 감시를 활성화한다.

## 토폴로지

```text
Operator ─ Router ─ Firewall ─ Service Node
                              ├─ 22/TCP
                              ├─ 53/UDP
                              └─ 8080/TCP
```

## 숨겨진 문제

- 관리 웹 서비스는 `8080/TCP`에서 실행된다.
- `80/TCP`는 닫혀 있어 RST를 반환한다.
- `443/TCP`는 방화벽이 드롭한다.
- `22/TCP`는 SSH이지만 현재 목표가 아니다.

## 플레이 흐름

1. ping 성공으로 IP 경로가 정상임을 확인한다.
2. 임무 로그에서 후보 포트 `80`, `443`, `8080`을 확보한다.
3. `TCP Needle`로 한 포트씩 SYN을 보낸다.
4. 80번에서는 RST가 돌아온다.
5. 443번에서는 방화벽이 패킷을 파괴해 시간 초과가 발생한다.
6. 8080번에서는 SYN-ACK가 돌아온다.
7. ACK를 보내 3-way handshake를 완성한다.
8. 연결된 세션에서 서비스 배너를 확보한다.

## 핵심 퍼즐

연결 거부, 시간 초과, SYN-ACK가 서로 다른 의미를 가진다는 사실을 결과 애니메이션으로 구분한다.

## Trace 규칙

- 후보 포트 단일 조사: +2
- 단서 없이 범위 조사: +15
- 동일 포트 반복 조사: +5
- 열린 포트 정확히 식별: Trace 일부 회복

## 잘못된 행동과 반응

| 결과 | 게임 연출 | 의미 |
|---|---|---|
| RST | 패킷이 서버에서 즉시 반사 | 호스트 도달, 포트 닫힘 |
| Timeout | 방화벽에서 패킷 소멸 | 필터링 또는 응답 부재 |
| SYN-ACK | 서버 포트가 열리고 응답 발사 | TCP 연결 가능 |
| UDP 오사용 | 응답 확인 없이 패킷만 전달 | TCP 서비스에 맞지 않는 방식 |

## 클리어 연출

SYN, SYN-ACK, ACK 세 패킷이 삼각형 형태로 결합해 세션 채널을 만든다. 8080 포트의 잠금이 열리고 `SERVICE CHANNEL OPEN`이 표시된다.

## 선택 과제

- Trace 10 이하로 완료
- 3개 이하의 포트만 조사
- TCP 플래그를 올바른 순서로 선택

## 이 스테이지가 가르치는 것

호스트에 도달하는 것과 특정 서비스에 연결하는 것은 다르며, 포트 반응은 문제 원인을 구분하는 중요한 단서다.

# Stage 6. 이름을 잃은 서버

## 핵심 정보

| 항목 | 내용 |
|---|---|
| 주요 계층 | L7 DNS, L4 UDP/TCP |
| 예상 시간 | 15~20분 |
| 난이도 | 보통 |
| 핵심 개념 | 도메인 이름, A 레코드, DNS 서버, TTL, 캐시 |
| 새 도구 | DNS Query, Resolver Config, Cache Viewer |

## 임무 브리핑

다음 목표는 `vault.nexus.local`이라는 이름으로만 기록되어 있다. 기존 DNS 서버는 오염된 주소를 반환하거나 응답하지 않는다.

## 토폴로지

```text
                        ┌─ DNS-A: 정상
Operator ─ Router ──────┤
                        ├─ DNS-B: 오래된 정보
                        └─ Vault Server
```

## 숨겨진 문제

- Operator PC는 오래된 DNS-B를 사용한다.
- DNS-B에는 만료된 주소가 남아 있다.
- 임무 로그에 정상 DNS-A 주소의 일부가 기록되어 있다.
- 정상 응답의 A 레코드가 실제 Vault Server를 가리킨다.

## 플레이 흐름

1. 도메인으로 접속하지만 이름 해석에 실패한다.
2. Resolver Config에서 현재 DNS 서버를 확인한다.
3. DNS-B의 응답 TTL이 만료되었음을 발견한다.
4. 네트워크 로그에서 정상 DNS-A 주소를 복구한다.
5. Resolver를 DNS-A로 변경한다.
6. `vault.nexus.local`의 A 레코드를 질의한다.
7. 이름 문자열이 IP 주소로 변환된다.
8. 반환된 IP와 TTL을 증거 노트에 저장한다.
9. 도메인 이름으로 Vault Server에 접속한다.

## 핵심 퍼즐

플레이어는 이름, DNS 서버, 최종 서비스 서버를 서로 다른 대상으로 구분해야 한다.

## 플레이어가 얻는 단서

- `Name resolution failed`
- Resolver: DNS-B
- Cache entry: `EXPIRED`
- DNS-A 로그 조각
- 정상 A 레코드와 TTL

## 잘못된 행동과 반응

| 행동 | 게임 반응 |
|---|---|
| 웹 서버에 DNS Query 전송 | 서버가 해당 서비스 포트를 제공하지 않음 |
| 만료된 캐시 강제 사용 | 패킷이 존재하지 않는 예전 서버 위치로 이동 |
| 잘못된 레코드 종류 선택 | 필요한 IPv4 주소가 반환되지 않음 |

## 클리어 연출

깨져 있던 도메인 글자가 재조립되고 IP 주소로 변환된다. 안개 속에 숨겨져 있던 Vault Server가 토폴로지에 나타나며 `TARGET RESOLVED`가 표시된다.

## 선택 과제

- 오래된 IP로 패킷을 보내지 않고 완료
- DNS 질의 2회 이하
- TTL 의미 확인

## 이 스테이지가 가르치는 것

DNS는 서비스 자체가 아니라 이름을 주소로 해석하는 별도의 시스템이며, 캐시 정보에는 유효 시간이 있다.

# Stage 7. 서버의 언어

## 핵심 정보

| 항목 | 내용 |
|---|---|
| 주요 계층 | L7 응용 계층 |
| 예상 시간 | 18~25분 |
| 난이도 | 보통 |
| 핵심 개념 | HTTP 메서드, 경로, Host, 헤더, 상태 코드 |
| 새 도구 | HTTP Builder, Response Decoder |

## 임무 브리핑

관리 서버와 TCP 연결은 완료되었다. 하지만 서버는 플레이어가 보내는 요청을 이해하지 못한다. 응답 코드와 헤더를 단서로 올바른 요청을 구성해야 한다.

## 토폴로지

```text
Established TCP Session
Operator ═══════════════ Management API :8080
```

## 숨겨진 문제

정상 요청은 다음 조건을 요구한다.

- Host: `ops.nexus.local`
- Method: `GET`
- Path: `/api/status`
- Accept: `application/json`

정답을 직접 제공하지 않고 서버 응답이 각 조건의 단서를 순차적으로 알려 준다.

## 플레이 흐름

1. 기본 `GET /` 요청을 전송한다.
2. 서버가 `302 Found`와 `Location: /api/status`를 반환한다.
3. 새 경로에 `POST`를 보내면 `405 Method Not Allowed`와 `Allow: GET`이 돌아온다.
4. `GET /api/status`를 보내지만 Host가 달라 `404`가 반환된다.
5. 이전 DNS 증거에서 올바른 Host를 선택한다.
6. `Accept: application/json`을 포함해 요청한다.
7. 서버가 `200 OK`와 JSON 상태 데이터를 반환한다.

## 핵심 퍼즐

실패 응답도 다음 요청을 구성하는 단서로 사용해야 한다.

## HTTP 응답의 게임 표현

| 상태 | 연출 | 플레이 의미 |
|---|---|---|
| 302 | 응답 카드에서 새로운 경로 화살표 생성 | 다른 위치로 이동 |
| 400 | 잘못된 필드가 붉게 분해 | 요청 형식 문제 |
| 404 | 서버가 빈 경로 지도를 반환 | Host 또는 경로 문제 |
| 405 | 사용한 메서드 카드가 튕기고 `Allow` 표시 | 메서드 변경 필요 |
| 200 | 응답 데이터가 잠금 해제 | 요청 성공 |

## 잘못된 행동과 반응

- 같은 요청을 반복하면 서버가 동일 응답을 반환하고 Trace가 소폭 오른다.
- 존재하지 않는 경로를 무작위 시도하면 요청 카드가 서버의 빈 디렉터리에서 소멸한다.
- JSON이 필요한 응답에 다른 Accept를 사용하면 콘텐츠 협상 실패 단서가 나타난다.

## 클리어 연출

메서드, Host, Path, Header 카드가 하나의 HTTP 메시지로 결합된다. 서버가 이를 해석한 뒤 JSON 데이터 블록을 방출하고 `APPLICATION ACCESS GRANTED`가 표시된다.

## 선택 과제

- HTTP 요청 4회 이하
- 응답 헤더 단서를 모두 증거 노트에 기록
- 4xx 응답 없이 최종 요청 완성

## 이 스테이지가 가르치는 것

HTTP는 단순 URL 접속이 아니라 메서드, 경로, 헤더와 응답 의미를 가진 메시지 프로토콜이다.

# Stage 8. 믿을 수 없는 얼굴

## 핵심 정보

| 항목 | 내용 |
|---|---|
| 주요 계층 | L5~L7, TLS, HTTPS |
| 예상 시간 | 18~25분 |
| 난이도 | 보통 이상 |
| 핵심 개념 | 암호화, 인증서, 호스트명, 신뢰, HTTPS |
| 새 도구 | TLS Inspector, Certificate Chain Viewer |

## 임무 브리핑

보안 서버와 443/TCP 연결에는 성공했지만, 서버가 제시한 신원을 신뢰할 수 없다. 경고를 무시하면 빠르게 진행할 수 있지만 미끼 서버에 접속할 위험이 있다.

## 토폴로지

```text
                    ┌─ Secure Gateway
Operator ─ Firewall ┤
                    └─ Decoy Gateway
```

## 숨겨진 문제

- 플레이어는 Secure Gateway의 IP로 직접 접속하고 있다.
- 인증서 SAN은 `secure.nexus.local`이다.
- Decoy Gateway는 비슷한 이름의 자체 서명 인증서를 사용한다.
- 올바른 DNS 이름으로 접속해야 인증서 이름 검증이 성공한다.

## 플레이 흐름

1. IP 주소로 HTTPS 접속을 시도한다.
2. TCP 연결은 성공하지만 TLS 단계에서 인증서 이름 불일치가 발생한다.
3. `TLS Inspector`로 인증서의 SAN, 발급자, 유효 기간을 확인한다.
4. SAN에서 `secure.nexus.local`을 발견한다.
5. DNS Query로 해당 이름의 주소를 확인한다.
6. 도메인 이름과 올바른 SNI를 사용해 다시 연결한다.
7. 인증서 체인과 이름 검증이 모두 성공한다.
8. 보호된 HTTPS 채널이 열린다.

## 선택의 함정

`인증서 검증 무시` 버튼을 제공할 수 있지만 정답으로 처리하지 않는다.

검증을 무시하면:

- 빠르게 연결되는 것처럼 보인다.
- 채널 색상이 불안정한 붉은색으로 표시된다.
- Decoy Gateway가 잘못된 데이터를 반환한다.
- Trace가 크게 증가한다.
- 플레이어는 다시 인증서를 조사해야 한다.

## 잘못된 행동과 반응

| 실패 | 연출 |
|---|---|
| 이름 불일치 | 인증서와 요청 이름이 겹치지 않고 균열 |
| 기간 만료 | 인증서 시간이 빠르게 지나가며 붉게 변함 |
| 신뢰되지 않은 발급자 | 인증서 체인이 중간에서 끊어짐 |
| 검증 무시 | 보호막은 생성되지만 내부에 붉은 노이즈 발생 |

## 클리어 연출

ClientHello와 ServerHello 패킷이 교차하고 양쪽 키 조각이 맞물린다. 보라색 TLS 보호막이 세션 전체를 감싸며 `IDENTITY VERIFIED`가 표시된다.

## 선택 과제

- 인증서 검증을 끄지 않고 완료
- Decoy Gateway와 세션을 만들지 않음
- SAN, 발급자, 유효 기간을 모두 확인

## 이 스테이지가 가르치는 것

암호화되었다는 사실만으로 안전한 것이 아니며, 통신 상대의 신원도 검증해야 한다.

# Stage 9. 잠긴 원격 셸

## 핵심 정보

| 항목 | 내용 |
|---|---|
| 주요 계층 | L7 SSH, 인증, 세션 |
| 예상 시간 | 20~30분 |
| 난이도 | 어려움 |
| 핵심 개념 | SSH 서비스, 호스트 키, 사용자 키, 원격 셸 |
| 새 도구 | SSH Client, Key Ring, Remote Terminal |

## 임무 브리핑

중앙 서버의 복구 장치에 접근하려면 원격 셸을 열어야 한다. 플레이어에게는 사용자 후보와 여러 키가 있지만, 먼저 접속 대상이 진짜 서버인지 확인해야 한다.

## 토폴로지

```text
Operator ═══ Encrypted Network ═══ Recovery Server :22
```

## 숨겨진 문제

- 서버 호스트 키 지문은 브리핑 문서 조각에 나뉘어 있다.
- 올바른 사용자는 `operator`다.
- 올바른 개인 키의 라벨은 `operator@recovery`다.
- 접속 후에도 서비스 로그를 분석해야 한다.

## 플레이 흐름

1. 22/TCP에서 SSH 배너를 확인한다.
2. 서버가 제시한 호스트 키 지문을 확인한다.
3. 이전 스테이지에서 확보한 문서 조각과 지문을 비교한다.
4. 서버 신원이 일치하면 접속을 계속한다.
5. 사용자 `operator`를 선택한다.
6. Key Ring의 메타데이터를 보고 올바른 키를 선택한다.
7. 키 기반 인증에 성공한다.
8. 제한된 원격 셸이 열린다.
9. `status`로 장애 서비스를 확인한다.
10. `logs`로 실패 원인을 조사한다.
11. 올바른 서비스만 `restart`한다.
12. `verify`로 복구 상태를 확인한다.

## 셸 조작

명령어를 전부 암기하게 하지 않는다.

- 입력 자동완성 제공
- 현재 사용할 수 있는 명령 카테고리 제공
- 명령 결과는 실제 로그 형태로 출력
- 잘못된 명령은 정답 실패보다 추가 정보 부족으로 처리

## 잘못된 행동과 반응

| 행동 | 게임 반응 |
|---|---|
| 호스트 키 불일치 무시 | 셸 화면에 지속적인 미끼 데이터와 경고 |
| 잘못된 사용자 | 인증 채널 첫 잠금에서 차단 |
| 잘못된 개인 키 | 두 번째 잠금이 닫히며 `publickey` 오류 |
| 무작위 인증 반복 | Trace 크게 증가 |
| 잘못된 서비스 재시작 | 다른 서비스가 잠시 중단되지만 복구 가능 |

## 클리어 연출

호스트 키와 사용자 키가 서로 다른 두 잠금 장치를 차례로 연다. 터미널 채널이 서버까지 뻗고, 복구 명령 실행 시 서버 코어가 재부팅되며 `REMOTE CONTROL ACQUIRED`가 표시된다.

## 선택 과제

- 인증 실패 없이 접속
- 로그 확인 후 정확한 서비스만 재시작
- 최소 명령 수로 복구

## 이 스테이지가 가르치는 것

SSH에서는 서버 신원 확인과 사용자 인증이 별개의 단계이며, 접속 이후에도 로그를 근거로 작업해야 한다.

# Stage 10. FULL STACK BREACH

## 핵심 정보

| 항목 | 내용 |
|---|---|
| 주요 계층 | L1~L7 전체 |
| 예상 시간 | 35~50분 |
| 난이도 | 최종 임무 |
| 핵심 개념 | 계층별 장애 격리와 전체 통신 흐름 |
| 사용 도구 | Stage 1~9 전체 도구 |

## 임무 브리핑

`NULL`이 NEXUS 중앙 업데이트 서버를 장악했다. 30분 후 모든 훈련 노드에 손상된 설정이 배포된다.

플레이어는 외부 복구 단말에서 시작해 중앙 서버까지 통신 경로를 만들고, 보안 API에서 단기 SSH 인증서를 발급받은 뒤 원격 셸로 배포 서비스를 중단해야 한다.

## 토폴로지

```text
Recovery PC
  └─ Access Switch
      └─ Edge Router
          └─ Security Firewall
              ├─ Internal DNS
              ├─ Decoy Server
              └─ Update Server
                   ├─ HTTPS Management :8443
                   └─ SSH Recovery     :22
```

## 초기 장애

1. Recovery PC의 주 인터페이스가 비활성화되어 있다.
2. 기본 게이트웨이가 삭제되어 있다.
3. Edge Router에서 중앙망 정적 경로가 손상되어 있다.
4. DNS 설정이 오래된 서버를 가리킨다.
5. 관리 API는 표준 443이 아닌 8443/TCP에서 실행된다.
6. Update Server 인증서는 `update.nexus.local` 이름에만 유효하다.
7. 인증서 발급 API는 정확한 HTTP 메서드와 JSON 본문을 요구한다.
8. 발급된 SSH 인증서는 `recovery` 사용자에게만 유효하다.
9. 접속 후 실제 중단 대상 서비스를 로그에서 찾아야 한다.

## 임무 단계

### Phase 1. 신호 복구

- Recovery PC의 올바른 인터페이스를 활성화한다.
- 스위치 링크를 확인한다.
- 게이트웨이 MAC을 ARP로 확보한다.

### Phase 2. 경로 복구

- IP와 서브넷을 확인한다.
- 기본 게이트웨이를 설정한다.
- traceroute로 패킷이 Edge Router 이후 사라지는 것을 발견한다.
- 중앙망 정적 경로를 복구한다.

### Phase 3. 대상 발견

- 오래된 DNS 설정을 교체한다.
- `update.nexus.local`의 올바른 A 레코드를 얻는다.
- Decoy Server와 실제 Update Server를 구분한다.

### Phase 4. 보안 채널 생성

- 후보 포트에서 8443/TCP를 발견한다.
- TLS 인증서의 SAN과 발급자를 확인한다.
- 올바른 이름으로 HTTPS 세션을 만든다.

### Phase 5. 인증서 발급

- API 루트 요청의 응답을 분석한다.
- 올바른 경로, 메서드와 JSON 형식을 구성한다.
- 제한 시간이 있는 단기 SSH 인증서를 발급받는다.

### Phase 6. 중앙 서버 복구

- SSH 호스트 키를 확인한다.
- `recovery` 사용자와 단기 인증서를 사용한다.
- 로그에서 손상 배포 서비스 `null-agent`를 찾는다.
- 서비스를 중단하고 정상 설정을 복구한다.
- HTTPS 상태 API로 최종 검증한다.

## 분기와 압박

### Trace

최종 스테이지에서는 Trace가 실제 환경 변화에 영향을 준다.

| Trace | 변화 |
|---:|---|
| 0~39 | 정상 |
| 40~59 | 방화벽 검사 속도 증가 |
| 60~79 | 일부 포트가 일시적으로 숨겨짐 |
| 80~99 | Decoy Server가 가짜 응답 전송 |
| 100 | 세션 종료 후 마지막 체크포인트에서 재시작 |

### SSH 인증서 시간

인증서는 발급 후 제한 시간 동안만 유효하다. 단, 초보자가 막히지 않도록 시간 만료 시 API를 통해 재발급할 수 있다.

### 선택 경로

- 낮은 Trace로 정확히 조사하는 정밀 경로
- 에너지를 많이 사용해 빠르게 분석하는 고속 경로
- 힌트를 사용해 안정적으로 진행하는 지원 경로

어떤 경로를 선택해도 클리어할 수 있지만 결과 랭크가 달라진다.

## 최종 실패 연출

실패 원인에 따라 체크포인트가 다르다.

- Trace 100: 방화벽이 모든 세션을 차단
- 인증서 만료: SSH 잠금이 다시 닫힘
- Decoy 접속: 거짓 복구 화면 후 이상 신호 발견
- 잘못된 서비스 중단: 네트워크 일부가 암전되지만 재복구 가능

즉시 처음부터 다시 시작시키지 않고, 실패에서 얻은 증거를 유지한다.

## 최종 클리어 연출

1. `null-agent` 프로세스가 정지한다.
2. 중앙 서버의 붉은 코어가 청록색으로 변한다.
3. 복구 데이터가 SSH 채널을 통해 퍼진다.
4. 방화벽, 라우터, 스위치가 역순으로 정상화된다.
5. L1부터 L7까지 계층 링이 차례로 활성화된다.
6. 지금까지 사용한 대표 패킷이 전체 경로를 재생한다.
7. 도시 네트워크가 하나씩 점등된다.
8. `NEXUS RESTORED`와 최종 랭크가 표시된다.

## 랭크 기준

| 랭크 | 조건 예시 |
|---|---|
| S | 낮은 Trace, 힌트 없음, 인증 실패 없음, 최소 변경 |
| A | 일부 재시도 또는 개념 힌트 사용 |
| B | 여러 실패 후 정상 복구 |
| Assisted | 전체 행동 힌트를 사용해 완료 |

힌트 사용 여부와 관계없이 최종 성공 연출은 동일하게 제공한다.

## 이 스테이지가 가르치는 것

복잡한 네트워크 문제는 한 번에 해결하는 것이 아니라 낮은 계층부터 통신 조건을 검증하며 원인을 좁혀 가야 한다.

# 캠페인 전체 보상 구조

## 도구 해금

```text
Stage 1  Link Tester
Stage 2  ARP Pulse
Stage 3  Subnet Lens
Stage 4  Route Pulse
Stage 5  TCP Needle
Stage 6  DNS Query
Stage 7  HTTP Builder
Stage 8  TLS Inspector
Stage 9  SSH Client
Stage 10 전체 도구 조합
```

## 수집 요소

각 스테이지에는 세 종류의 수집 요소가 있다.

- `Protocol Fragment`: 프로토콜 핵심 개념 카드
- `Clean Log`: 불필요한 행동 없이 얻는 완전한 통신 로그
- `NULL Trace`: 캠페인 배후 스토리를 보여 주는 숨겨진 데이터

## 재도전 요소

- 낮은 Trace 달성
- 최소 행동 수
- 힌트 없이 완료
- 모든 패킷 분석 과제 완료
- 숨겨진 로그 발견
- S 랭크 획득

# 스테이지 제작 공통 규칙

모든 스테이지는 다음 조건을 만족해야 한다.

1. 정답 선택 버튼만으로 클리어할 수 없다.
2. 최소 하나 이상의 패킷 또는 장비 상태를 직접 관찰해야 한다.
3. 실패 결과가 다음 행동을 추론할 수 있는 정보를 제공한다.
4. 해결하려는 네트워크 계층이 화면 연출로 구분된다.
5. 무작위 도구 사용보다 증거 기반 행동이 유리하다.
6. 개념을 몰라도 단계별 힌트를 사용하면 완료할 수 있다.
7. 한 번 배운 도구가 이후 스테이지에서도 다시 사용된다.
8. 마지막 행동은 설정 입력이 아니라 실제 통신 성공으로 검증한다.
9. 성공과 실패가 서로 다른 시각·음향 피드백을 가진다.
10. 클리어 후 왜 성공했는지 패킷 경로를 다시 보여 준다.
